# frameact core perf pass — Implementation Plan (perf/core-preact)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Cut what an app pays per signal write on frameact's default path (write → `notify` → `tickEnd` → `flushSync()` → effect run) without touching a single semantic: the js-reactivity-benchmark family geomeans go from kairo 2.08× / s 1.83× / dynamic 1.52× (relative to the fastest engine) to about 1.6× / 1.6× / 1.4×, and the plain `1 signal → 1 effect + flush` round trip from 174 ns to 98 ns.

**Architecture:** Three measured changes, ordered by payoff. (1) `fasterdom.flushSync()` returns early when all three task queues are empty instead of running a pass that only toggles the phase twice and allocates three arrays. (2) The `tickEnd` queue in `schedulers.ts` becomes one array reused for the life of the module (head/length indices, slots cleared as they run) and books its end-of-tick microtask once per tick instead of once per empty → non-empty transition — on a write/`flushSync()` loop that removes two allocations and a Promise per write. (3) The effect run path loses two indirections: `createEffect` stores the user's compute as is and `update()` passes `prev` itself (no wrapper closure per effect), `computeNode` dispatches DIRTY effects straight to `update()`, and `update()` inlines the three-line `cleanup()`. Everything else that was tried measured within noise and is documented below so nobody re-tries it blind.

**Tech Stack:** TypeScript 7 (strict), pnpm, Vite 8 + vitest 5 + jsdom 30, oxlint. No new dependencies. Benchmarks: `bench/reactivity` (upstream js-reactivity-benchmark at `2c273f1`, adapter unchanged), `bench/store/core.bench.ts`, `bench/dom/*.bench.test.ts`.

**Spec:** `docs/superpowers/specs/2026-10-11-frameact-design.md` §3.1 (fasterdom phases, `flushSync`), §3.2 (core: links, latch, two-phase effects, `tickEnd` loop guard "counts runs per drain"), §3.5 (store walks / parking flags — not touched). ### Attribution (CPU profiles at 50–200 µs sampling, `--trace-deopt`, `--trace-gc`, line-level ticks)

- **Confirmed, the big one — effect scheduling allocations and the empty frame pass.** Per write on the default path the base allocated a fresh `[callback]` array and a `Promise.resolve().then(...)` chain (`onTickEnd`), and `fasterdom.flushSync()` ran a full pass over empty queues (three `[]` allocations, four `setPhase` toggles, three `forEach` calls). avoidablePropagation's profile was 34 % garbage collector + 6 % `flushSync$1` + 3 % `setPhase` + 2 % `runMeasureTasks`; after Tasks 1–2 `--trace-gc` counts 48 scavenges (7.5 ms) for the whole case and the GC bucket is gone. - **Confirmed, small — two indirections on the effect run path** (the per-effect wrapper closure around the user's compute; `computeNode` → `updateCheck` → `update` for an effect that is already DIRTY; the `cleanup()` call). Task 3: −10 % on the sync-effect micro (52 → 47 ns), −3 % on the diamond micro (433 → 421 ns), within noise on the jrb suites.

- **Refuted — link reuse misses.** An instrumented bundle counted new `Link` allocations per iteration: 0 on every kairo shape except `unstable` (2 per write — the read order alternates; alien-signals allocates the same). Update counts per iteration equal alien's (diamond 7, broad 150, mux 103, avoidable 2).
- **Refuted — equality cutoff.** avoidablePropagation does exactly 2 updates per write (c1, c2) and the effect's `updateCheck` resolves CLEAN; the whole 3.9× was scheduling + GC (now 1.8×).
- **Mostly refuted — store/parking flags in `notify`/`update`.** Line-level ticks put the `storeWalk` branch and the `F_UNSURE|F_STORE|F_PARKED` masks at ≤ 2 % of `notify` self time; `update()`'s `storeCause` and the flag masks are ~4 %. Not worth a separate fast path.

Where the remaining ~1.6× lives (frameact / alien, ns, isolated micros on the prod bundle): write+notify+schedule+flush+run of `1 signal → 1 effect` 69 / 36 (Preact 52); the same with a sync custom schedule — no queue, no flush — 47, so queue + drain ≈ 22 ns; `signal → memo → effect` 121 / 59; diamond(5) 482 / 238; broad(50) 9.1 / 3.7 µs; pull only (`write` then `memo()` with no effect) 37 / 34 — the graph itself is at alien's level, the effect pipeline and `update()` are not.
```ts
let onTickEndCallbacks: NoneToVoidFunction[] | undefined;
/** Nesting depth of flushTickEnd(): > 0 while a drain is running (a callback may call flushSync()). */
let tickDrainDepth = 0;
/** Bumped once at the start of every outermost flushTickEnd() drain that has work to do. */
let tickDrainEpoch = 0;

export function onTickEnd(callback: NoneToVoidFunction) {
  if (!onTickEndCallbacks) {
    onTickEndCallbacks = [callback];
    // While draining, the running drain picks the new callback up: no extra microtask.
    if (tickDrainDepth === 0) Promise.resolve().then(flushTickEnd);
  } else {
    onTickEndCallbacks.push(callback);
  }
}

/**
 * Run pending onTickEnd callbacks until none are left: callbacks queued while flushing run in this
 * same flush, so a cascade (effect → write → effect ...) completes in one drain. Used by the
 * microtask itself and by flushSync(). A re-entrant call (a callback calling flushSync()) drains
 * the pending callbacks too, within the same drain epoch.
 */
export function flushTickEnd() {
  if (!onTickEndCallbacks) return;
  if (tickDrainDepth === 0) tickDrainEpoch++;
  tickDrainDepth++;
  try {
    while (onTickEndCallbacks) {
      const currentCallbacks = onTickEndCallbacks;
      onTickEndCallbacks = undefined;
      for (let i = 0; i < currentCallbacks.length; i++) safeExec(currentCallbacks[i]);
    }
  } finally {
    // Only reached with work left if something escaped safeExec (e.g. a throwing console.error):
    // re-book the microtask that onTickEnd skipped while we were draining, or the queue would stall.
    if (--tickDrainDepth === 0 && onTickEndCallbacks) Promise.resolve().then(flushTickEnd);
  }
}

/** @internal core flushSync() loops until nothing is pending. */
export function hasPendingTickEnd() {
  return onTickEndCallbacks !== undefined;
}
```

with

```ts
/**
 * The tickEnd queue (frameact, perf): ONE array reused for the life of the module —
 * `tickQueue[tickHead .. tickLen)` are the pending callbacks. A drain runs them in order (callbacks
 * queued meanwhile land behind `tickLen` and are taken by the same loop) and resets both indices
 * once the queue is empty; the backing store is kept, so neither scheduling nor draining allocates.
 * (Before: a fresh array per empty → non-empty transition, and a Promise per transition — on a
 * write/flushSync() loop that was two allocations per write.)
 */
const tickQueue: (NoneToVoidFunction | undefined)[] = [];
let tickHead = 0;
let tickLen = 0;
/**
 * True while the end-of-tick microtask is booked and has not run yet. It is booked once per tick,
 * not once per empty → non-empty transition: a flushSync() in between drains the queue but leaves
 * the microtask booked, and the next onTickEnd() before it fires reuses it (it drains whatever is
 * pending by then; usually nothing).
 */
let tickBooked = false;
/** Nesting depth of flushTickEnd(): > 0 while a drain is running (a callback may call flushSync()). */
let tickDrainDepth = 0;
/** Bumped once at the start of every outermost flushTickEnd() drain that has work to do. */
let tickDrainEpoch = 0;

function flushTickEndMicrotask() {
  tickBooked = false;
  flushTickEnd();
}

export function onTickEnd(callback: NoneToVoidFunction) {
  tickQueue[tickLen++] = callback;
  // While draining, the running drain picks the new callback up: no extra microtask.
  if (!tickBooked && tickDrainDepth === 0) {
    tickBooked = true;
    Promise.resolve().then(flushTickEndMicrotask);
  }
}

/**
 * Run pending onTickEnd callbacks until none are left: callbacks queued while flushing run in this
 * same flush, so a cascade (effect → write → effect ...) completes in one drain. Used by the
 * microtask itself and by flushSync(). A re-entrant call (a callback calling flushSync()) drains
 * the pending callbacks too, within the same drain epoch.
 */
export function flushTickEnd() {
  if (tickHead === tickLen) return;
  if (tickDrainDepth === 0) tickDrainEpoch++;
  tickDrainDepth++;
  try {
    while (tickHead < tickLen) {
      const callback = tickQueue[tickHead]!;
      tickQueue[tickHead++] = undefined; // (let the callback go: the slot is reused later)
      safeExec(callback);
    }
  } finally {
    if (--tickDrainDepth === 0) {
      if (tickHead === tickLen) {
        tickHead = tickLen = 0;
      } else if (!tickBooked) {
        // Only reached with work left if something escaped safeExec (e.g. a throwing console.error):
        // re-book the microtask that onTickEnd skipped while we were draining, or the queue would stall.
        tickBooked = true;
        Promise.resolve().then(flushTickEndMicrotask);
      }
    }
  }
}

/** @internal core flushSync() loops until nothing is pending. */
export function hasPendingTickEnd() {
  return tickHead !== tickLen;
}
```

Notes for the implementer: the array only grows to the largest burst ever queued (slots are cleared as they run, indices reset when empty), so it holds no callbacks between ticks; a nested drain (depth > 1) never resets the indices — the outer loop continues from the shared `tickHead`; `tickEnd`'s loop guard in `effects.ts` (`isTickDraining()`/`getTickDrainEpoch()`) is untouched and still counts runs per drain.

## Risks and what guards them

- **`tickEnd` queue (Task 2).** A microtask that stays booked across a synchronous drain fires later on an empty queue — a no-op (`flushTickEnd` returns before bumping the epoch, so `'the drain epoch advances once per outermost drain: not for nested flushes, not for empty ones'` still holds). A callback that escapes `safeExec` (a throwing `console.error`) leaves `tickHead < tickLen`: the `finally` re-books the microtask unless one is already booked — either way the queue drains (`'a throwing flushTickEnd callback does not drop the rest of the batch'`). The array retains its maximum length (bounded by the largest burst in one tick); callbacks are released as they run. A re-entrant drain shares `tickHead` with the outer loop, so nothing runs twice (second new test).
- **`flushSync` early return (Task 1).** Phase listeners (`onPhaseChange`: stricterdom) no longer see four toggles on an empty pass; stricterdom only drains `MutationRecord`s at those changes and nothing ran in between, so there is nothing to attribute differently. The end state is identical (`setPhase('measure')`).
- **Effect compute `this` (Task 3).** A `function`-style effect compute now sees `this === node` (as memo computes always did) instead of `undefined`. No API documents `this`; arrow functions (the compiler's output and every test) are unaffected.
- **`node._disposal !== null` vs the old truthiness check** — `_disposal` is `null`, a `Disposable` (an object or function) or an array; never `0`/`''`. Same branch.
