# frameact — дизайн v1

Дата: 2026-10-11. Статус: ревизия 2 — после adversarial review (см. §9).

## 1. Что это и зачем

**frameact** — fine-grained реактивный UI-фреймворк на сигналах, который реализует
принципы рендеринга teact (Telegram Web A):

- **один проход на кадр** — вся работа графа и все записи в DOM планируются в один
  `requestAnimationFrame`, по одной задаче на фазу;
- **явные фазы** `measure → mutate → forced-reflow measure → forced-reflow mutate` —
  чтение layout никогда не перемежается с записью в DOM;
- **гейтинг тяжёлых анимаций** — во время blocking-анимации кадровая работа
  откладывается целиком (атомарно, не по половине кадра), глобально или для поддерева;
- **stricterdom** — dev-режим, который ловит нарушения фаз на уровне DOM API и
  называет виновный эффект.

Вместо VDOM и ре-рендера компонентов — реактивный граф и точечные обновления DOM
(модель SolidJS). Компонент выполняется один раз; обновляются только биндинги.

Целевой потребитель — клиент мессенджера масштаба Telegram Web A: длинные списки,
высокочастотные обновления стора, много CSS/JS-анимаций, iOS Safari, mid-range Android.

### Чем это отличается от существующего

| | teact | Solid 1.x / 2.0 | frameact |
|---|---|---|---|
| Обновление | VDOM-дифф, ре-рендер компонента | fine-grained | fine-grained |
| Когда флашится | rAF, один проход | микротаск | rAF, один проход |
| Фазы measure/mutate | да | нет | да |
| Гейтинг анимаций | глобальный | нет | глобальный + per-subtree |
| Проверка нарушений фаз | stricterdom | нет | stricterdom + атрибуция до эффекта |

## 2. Принятые решения

| Вопрос | Решение | Почему |
|---|---|---|
| Ядро сигналов | Форк `maverick-js/signals` v6 (MIT, ~1k строк), вендорится в `src/core` | Код прост и закончен; планировщик там — одна функция, которую мы заменяем. Полное владение. `@solidjs/signals` 2.0 — 18k строк RC с транзакциями/lanes, флаш в микротаске захардкожен |
| Компилятор | `@solidjs/babel-plugin` 2.0 с `moduleName: "frameact/dom"` | Эмитит двухфазные эффекты `_$effect(compute, apply)` — чистое вычисление и DOM-запись уже разделены. Писать свой компилятор — отдельный проект |
| DOM-рантайм | Порт `dom-expressions` 1.x client (MIT), адаптированный к API, которое импортирует компилятор 2.0 | Стабилен годами, ~1k строк, не завязан на RC-семантику 2.0 |
| Flow-компоненты | Свои `For`/`Show`/`Switch`/`Match`/`Dynamic`/`Portal` поверх `mapArray` | ~300 строк; `solid-js` тянет `@solidjs/signals` |
| API для авторов | Чистый Solid-стиль: компонент выполняется один раз, пропсы-геттеры | Hooks-прослойка поверх fine-grained даёт худшее из обоих миров. Код из telegram-tt не переносится 1:1 — осознанно |
| Эффекты | Двухфазные `createEffect(compute, apply, schedule)`; **фаза = планировщик**; фасады `createEffect` / `createMeasureEffect` / `createMutationEffect` / `createIdleEffect` / `createRenderEffect` | Как `throttleWith(requestMeasure, fn)` в teact. Без строковых опций и без `equals` |
| Кадровые планировщики | Батчирующие очереди: одна fasterdom-задача на фазу на кадр; гейт сэмплируется один раз на дрен | Прямой `requestMeasure(run)` на каждый эффект давал частично применённые кадры, релиз гейта вне фаз и записи из compute, уезжающие в следующий кадр (§9) |
| Семантика записи | `set()` обновляет значение сразу, чтение сразу видит новое; эффекты ждут своего планировщика | Как Solid 1.x. Проще teact'овского `nextValue`, минусов для целевого приложения не найдено |
| Гейтинг анимаций | Blocking гейтит кадровые очереди по умолчанию; non-blocking — только стор и явный opt-in через `gateOnHeavyAnimation`; оба — глобально и per-subtree через scope. Scope гейтит **обновления**, не создание поддерева | Паритет с teact; «гейтить всё на non-blocking» заставило бы локальные UI-анимации ждать чужие |
| Стор | `frameact/store` — глобальный стор на сигналах: подписки на сущности, запись со структурным шарингом, гейтинг обновлений по scope (модель API — §3.5, на пересмотре) | Целевому приложению нужен глобальный стор; гейтинг обновлений требует интеграции с ядром |
| Контролируемые инпуты | Директивы `use:value` / `use:checked`, не атрибут `value=` | Компилятор 2.0 эмитит `el.value = v` напрямую — рантайму перехватить нечего (проверено по фикстурам) |
| События | Соглашения Solid: `onClick`, `onInput`, делегирование через document; `on:name` для нативных | Компилятор эмитит `addEvent(el, name, handler, delegate)` под эту модель |
| Refs | `ref={el => …}` / `ref={variable}` | Solid-стиль |
| Ошибки | Ошибка в compute/apply логируется (или уходит в ближайший `onError`-scope), узел остаётся CLEAN с предыдущим применённым значением, кадр продолжается | Teact'овская устойчивость. Solid 2.0 останавливает реактивность целиком — для мессенджера неприемлемо |
| Структура | Один пакет с subpath-экспортами | Монорепа не нужна до второго потребителя |

## 3. Архитектура

```
frameact                 — сигналы, эффекты и планировщики, flow-примитивы, heavyAnimation
frameact/scheduler       — fasterdom: rAF, фазы, requestMeasure/Mutation/ForcedReflow
frameact/dom             — рантайм для компилятора (moduleName), render, For/Show/…, директивы
frameact/stricterdom     — dev-only контроль фаз с атрибуцией
frameact/store           — глобальный стор на сигналах
frameact/vite            — Vite-плагин (обёртка @solidjs/babel-plugin)
```

Зависимости: `dom → core → scheduler`; `store → core`; `stricterdom ← scheduler`
(планировщик вызывает `setPhase`), `stricterdom ← core` (атрибуция, dev). `core` не
знает про DOM.

### 3.1 `scheduler` — fasterdom

Порт `teact/src/lib/fasterdom/fasterdom.ts` и `util/schedulers.ts`:

- `fastRaf(cb, withTimeoutFallback)` — объединяет колбэки в один rAF; фолбэк 35 мс
  через `setTimeout` для фоновых вкладок и iOS.
- Проход кадра:
  ```
  rAF:
    setPhase('measure');  measureTasks()
    microtask: setPhase('mutate');  mutationTasks()
    microtask: setPhase('measure'); forcedReflowTasks() → собирают mutation-колбэки
    microtask: setPhase('mutate');  forcedReflowMutationTasks()
    setPhase('measure')
  ```
  Микротаски между фазами нужны, чтобы колбэки `MutationObserver` stricterdom'а
  приходили с правильной фазой — порядок сохраняется как в teact.
- API: `requestMeasure(cb)`, `requestMutation(cb)`, `requestNextMutation(cb)`,
  `requestForcedReflow(cb)`, `onTickEnd`, `onIdle`, `throttleWith`.
- Сырые очереди fasterdom **не гейтятся** heavy animation — анимации пишут свои
  кадры через `requestMutation`, как в teact. Задачи, добавленные во время
  выполнения сырой очереди, уходят в следующий кадр (как в teact); очереди
  **run'ов** ядра (§3.2) дренируются до пустоты — это разные вещи.
- `flushSync()`: синхронный дрен всех четырёх очередей с корректным `setPhase`
  и сбросом `waiting` у throttle; реентер — ошибка в dev. Гейт `flushSync` **не**
  обходит. Нужен для тестов; `render()` в нём не нуждается (§3.3).

### 3.2 `core` — сигналы и эффекты

Файлы из maverick: `core.ts`, `signals.ts`, `map.ts`, `selector.ts`, `types.ts`,
`symbols.ts`. Алгоритм графа — Reactively: `CLEAN/CHECK/DIRTY`, `updateCheck`. Хранение
графа и правила latch'а изменены правками ниже. Меняется и то, что происходит, когда
эффект становится грязным.

#### Правки в maverick

1. **Граф на связях (как в alien-signals).** Вместо массивов `_sources`/`_observers`
   ребро — объект `Link` в двух двусвязных списках: в deps подписчика и в subs
   зависимости. Владение остаётся отдельным деревом: дети owner'а — интрузивный двусвязный
   список (`_lastChild`, `_prevSibling`/`_nextSibling`), добавление и удаление за O(1).
   Dispose итеративный (глубина дерева не ограничена стеком): дети раньше owner'а, в обратном
   порядке создания, поддерево ребёнка раньше него самого. Cleanup, который во время dispose
   диспозит соседа, потомка или предка, видит согласованное дерево; уже задиспозенные узлы
   повторно не диспозятся. Owner, созданный cleanup'ом под узлом, который сейчас диспозится (им
   самим или предком на стеке), и cleanup, зарегистрированный на этом узле, тоже диспозятся /
   выполняются (не больше 100 раундов, дальше — `console.error`). Если cleanup при пересчёте memo
   задиспозил саму memo, compute не выполняется.
   - Подписчик линкуется **по завершении чтения**, то есть после pull читаемой memo.
     Если pull бросил, линковка всё равно происходит; если pull задиспозил сам dep —
     нет.
   - Повторный прогон с тем же порядком чтений переиспользует связи по курсору
     `_depsTail` (без аллокаций). Связи, не прочитанные до конца compute, снимаются.
   - `version` связи — номер прогона подписчика, в котором она подтверждена.
   - `notify`/`updateCheck` итеративные (явный стек, реентерабельны), обход — pre-order
     DFS. Уровень обхода помнит номер прогона, на котором в него вошли. Связь,
     подтверждённая позже, пропускается: её compute начался после пометки узла и прочитал
     его свежим.
   - Запись результата computed'а помечает CHECK-подписчика DIRTY **без обхода под ним**
     (shallow, как в alien-signals): всё под ним уже помечено обходом, который сделал его CHECK,
     а вычисляющийся узел ниже, уже прочитавший его, этим обходом залатчен. Его подписчики
     узнают об изменении из его собственного `update()`. Исключения — вычисляющийся подписчик
     (правила latch) и узел с `F_UNSURE` (правка 6): к ним идёт обычный `notify`.
2. **Missed-wake latch.** Иначе запись в собственный источник во время compute
   (compute компонента вызывает экшен, который пишет в стор, который читает
   контейнер-предок) теряется: `notify` выходит по `_state >= DIRTY`, а `finally`
   ставит CLEAN. Наивный фикс «CLEAN до compute» неверен: ленивый pull computed'а
   внутри compute пишет свежий результат и даёт лишний пересчёт (ломает glitch-free
   «jagged diamond»).

   Поэтому узел помечается `F_COMPUTING` (бит в `_flags`), и `notify` на вычисляющийся
   узел **латчит** (`F_MISSED`):
   - запись сигнала — всегда;
   - запись результата computed'а — только если связь, по которой она пришла, уже
     подтверждена в текущем прогоне (`link.version === _depsTail.version`): значение
     прочитано и устарело. Иначе это ленивый pull, который прочитают свежим.

   Новая связь латчит сама, если dep записан после начала compute (`_writtenAt` против
   эпохи начала) или после своего pull остался не-CLEAN (сам себя залатчил). Исключение —
   dep ещё в своём `update()`.

   По окончании compute залатченный узел ре-дёргается обычным `notify(DIRTY)` (эффект
   перепланируется; dev-guard: 100 итераций → ошибка). Тот же механизм, что
   `REACTIVE_MISSED_WAKE` в Solid 2.0.
3. **Нет повторного входа в `update()`.** Синхронный эффект, разбуженный записью из
   compute memo (или её записью результата), может прочитать memo до конца её `update()`.
   Тогда пересчёта нет: читатель получает текущее значение, у узла ставится
   `F_REENTERED`. Изменившийся результат дойдёт до читателя обычным `notify`. Первый
   результат при `F_REENTERED` анонсируется подписчикам, если он `!==` значения `initial`,
   которое они видели.
4. **Пересканы в `updateCheck`.** Запись сигнала во время проверки deps узла может снова
   загрязнить уже проверенный dep. Источники такой записи: dep, залатчивший свою запись;
   пишущая memo, пересчитанная позже; синхронный эффект. Её `notify` останавливается на
   узле (он уже CHECK), и пометить его CLEAN значило бы оставить его устаревшим навсегда.

   Поэтому:
   - узел помнит `writeEpoch` на начало своего скана;
   - если при разрешении эпоха сдвинулась и какой-то dep снова CHECK/DIRTY (не считая
     dep, который ещё в своём `update()`), deps проверяются заново;
   - после `MAX_RESCANS` (4) узел пересчитывается консервативно. Это защита от compute,
     который бесконечно пишет то, что читает: его compute тянет deps, их следующие записи
     латчат узел, и на один pull приходится ограниченное число прогонов.
5. **`runTop` в ядре не используется** (см. жизненный цикл). `updateCheck` на
   `DISPOSED`-узле — no-op, а не перевод в `CLEAN`: DISPOSED-dep пропускается,
   DISPOSED-узел остаётся как есть. Задиспозенный узел снимает свои связи из subs
   зависимостей. Подписчики держат связи к задиспозенному dep до своего следующего
   прогона.
6. **Ошибки в compute.** Требование: ошибка никогда не замораживает часть UI навсегда.
   - **Memo держит ошибку.** Если compute memo бросил и `onError` владельца ошибку не взял, ошибка
     становится значением узла (флаг `F_ERRORED`, сама ошибка — в `_value`): каждое чтение её
     перебрасывает, пока compute не выполнится успешно. Неважно, где memo пересчиталась — в
     compute читателя или при проверке его deps в `updateCheck`: `try/catch` читателя видит
     ошибку всегда, а `updateCheck` не прерывается (dep, ставший ошибкой, — это изменение, читатель
     пересчитывается и читает его сам). Переходы «значение → ошибка» и «ошибка → значение» — изменение
     для подписчиков, даже если memo вернулась к прежнему значению; «ошибка → другая ошибка» —
     тоже изменение. Задиспозенная memo, державшая ошибку, бросает её и при чтении после dispose.
     Ошибку, взятую `onError`, memo не держит: читатели видят прежнее значение. Сама memo ничего не
     логирует: ошибку получает и сообщает тот, кто читает (эффект — в `console.error`).
   - **`F_THREW`.** Узел, чей compute бросил (взята ошибка или нет), при следующей проверке
     пересчитывается, даже если deps не изменились: прерванный прогон мог прочитать уже изменившиеся
     входы, а бросивший dep — восстановиться к прежнему значению.
   - **Первый успешный результат** memo, у которой первый прогон бросил, анонсируется подписчикам
     (они видели ошибку или `initial`).
   - **`F_UNSURE` — страховка.** Pull или обход, прерванный исключением, которого быть не должно
     (compute memo и планировщик не бросают наружу — см. выше и «Эффекты: ошибки»), оставил бы узлы
     грязными с непомеченными подписчиками. Такие узлы (при pull — транзитивно весь непроверенный
     грязный конус) получают `F_UNSURE`: следующий обход, дошедший до них, спускается к подписчикам,
     даже если узел уже грязный. На этом же держится shallow-пометка из правки 1.
   До этих правок (со времён maverick) эффект, у которого источник бросил двумя уровнями ниже, не
   перезапускался после восстановления, а `try/catch` в compute memo не видел ошибку dep'а,
   пересчитанного при проверке.

#### Эффекты: две половины, фаза = планировщик

```ts
type Schedule = (run: () => void, node: EffectNode) => void;

createEffect(compute, apply, schedule: Schedule = tickEnd)
// compute: (prev) => T                      — трекается, чистый, без DOM
// apply:   (value, prev) => void | cleanup  — без трекинга; здесь побочные эффекты

// фасады — публичный API
createEffect(compute, apply)          // tickEnd (микротаск): логика без DOM — сеть, стор
createMeasureEffect(compute, apply)   // frameMeasure: чтение layout
createMutationEffect(compute, apply)  // frameMutation: запись в живой DOM
createIdleEffect(compute, apply)      // idle: фоновая работа, когда нет анимаций
createRenderEffect                    // alias createMutationEffect — имя, которое ждёт компилятор

// кастомные планировщики
createEffect(c, a, frameForcedReflow)  // measure после mutate в том же кадре
createEffect(c, a, (run) => onIdle(run))
```

`Schedule` получает узел вторым аргументом: планировщик читает из него scope
(§heavyAnimation) и dev-метаданные. Поэтому `gateOnHeavyAnimation(requestMutation)`
можно безопасно создать один раз на уровне модуля.

Синхронный кастомный `Schedule` (`(run) => run()`) запускает эффект прямо из обхода `notify`:
эффект видит промежуточные состояния графа (ещё не помеченные memo) и платит повторными
прогонами — примерно по одному на каждый путь от записанного сигнала к эффекту. Планировщики на
очередях (`tickEnd`, кадровые очереди) запускают run после обхода и этой цены не платят.

Бросающий кастомный `Schedule` — ошибка его эффекта: она уходит в `console.error`, обход
продолжается (остальные подписчики узнают о записи), запись не бросает, а memo, чья запись
результата вызвала планировщик, не получает чужую ошибку. Эффект возвращается в CLEAN с
`F_THREW` и пересчитается при следующем изменении своих deps. Встроенные планировщики не бросают:
`tickEnd` (push в очередь, микрозадача, `setTimeout` после loop guard), кадровые очереди
(`enqueue` + `requestMeasure`/`requestMutation`; парковка на анимации ловит свои ошибки и
запускает run без гейта), `idle` (`onFullyIdle`), `gateOnHeavyAnimation` (подписка `once`).

**Поля узла:** `_value` (результат последнего compute), `_applied` (значение,
переданное в последний `apply`; сентинел `NOT_APPLIED` до первого), `_applyCleanup`,
`_scope` (heavy-animation scope, снимается при создании), `_schedule`; в dev —
`_name` (из компилятора или фасада), ссылка на owner с именем компонента.

**Жизненный цикл:**

1. *Создание.* `compute` выполняется синхронно (трекается, под текущим owner).
   Дальше — различие фасадов:
   - **mutation/render-эффекты:** `apply` выполняется **синхронно**. Нужно для
     атомарного создания поддерева: узлы в этот момент detached, stricterdom такие
     записи не считает нарушением (§3.4).
   - **все остальные** (`tickEnd`, `measure`, `idle`, кастомные): первый запуск — через
     `schedule(run, node)`. Measure-эффект, созданный внутри compute `insert`'а,
     впервые выполняется после attach, в следующей measure-фазе, и видит реальный
     layout. (`focus()`, `offsetHeight`, `scrollTop`-восстановление на монтировании —
     главный паттерн tt.)
2. *Загрязнение.* `notify` maverick'а при переходе из `CLEAN` → `schedule(run, node)`.
   Один вызов на грязный период — это и есть дедуп.
3. *`run`:*
   - узел `DISPOSED` → выход;
   - по owner-цепочке есть эффект в состоянии ≠ `CLEAN` → **выход без работы**
     (узел запоминается у ближайшего такого предка и перепланируется, когда тот
     закончит свой `run` — успешно или с ошибкой): его собственный `run` сделает
     cleanup и пересоздаст поддерево, этот узел будет задиспозен. Compute предка
     никогда не выполняется из чужого `run`. Сначала проверяется **вся** цепочка на
     эффекты; только если все чисты, грязные memo-предки дотягиваются сверху вниз.
     Строка `mapArray` — особый случай: memo списка ей не предок (она сосед скоупа
     строк), поэтому скоуп строк знает свою memo (`_mapMemo`), и run строки тянет её,
     если она не CLEAN, в общем порядке сверху вниз — на месте скоупа строк, после
     проверки всей цепочки на эффекты. Строка, чья сущность удалена вместе с её id,
     диспозится этим пуллом, а не выполняется с устаревшими данными (зомби-строки,
     план 3). Пулл карты, в отличие от пулла обычной memo, пишет в узлы item/index
     сохранённых строк и может загрязнить эффект-предок или внутреннюю карту, которые
     обход видел чистыми: после такого пулла цепочка проверяется заново (если тянутая
     memo осталась не CLEAN, то карта пересчитывается прямо сейчас, и повторного обхода
     нет). *Известное ограничение:* число повторных обходов ограничено числом скоупов
     списков в цепочке + 1 (каждую карту можно потянуть один раз, последний обход
     подтверждает чистоту цепочки). Цикл через вложенные списки — mapper внутреннего
     списка пишет в источник внешнего, и список растёт на каждом проходе — не виден
     счётчикам зацикливания по эффекту, поэтому без этой границы он крутился бы
     синхронно внутри одного `run`. При превышении повторные обходы прекращаются,
     в DEV выводится `console.error` с причиной, а эффект выполняется как обычно (дальше
     его ограничивают обычные защиты дрейна и self-dirty);
   - `_state = CLEAN`; пересчёт `compute` как computation графа (трекается). Первый
     compute упал → apply не вызывается вовсе. Если результат `=== _applied` — конец;
   - иначе: `_applyCleanup?.()`, `apply(_value, _applied)` без трекинга и **без
     owner** (как Solid 2.0): cleanup apply-половины — это **возвращённая функция**,
     она → `_applyCleanup`. `onCleanup` и создание owned-вычислений внутри apply —
     dev-ошибка (иначе одинаковый пересчёт compute сносил бы их без повторного apply);
     осознанное владение — через `runWithOwner`. `_applied = _value` — только если
     apply не бросил.
4. *Два канала cleanup.* `onCleanup` из compute (maverick `_disposal`) — перед каждым
   пересчётом compute и при dispose. `_applyCleanup` — **только** перед следующим
   `apply` и при dispose. Если dispose случился вне mutate-фазы (memo с условным
   поддеревом пересчитан при чтении в обработчике события), apply-cleanup'ы
   не выполняются на месте, а ставятся в кадровую mutate-очередь — иначе
   `classList.remove`/`disconnect` на attached-узлах выполняются в event handler.
5. *Ошибки.* Исключение в compute или apply → `handleError` по owner-цепочке
   (maverick `onError`); если не поймано — `console.error` с путём эффекта. Узел
   остаётся `CLEAN` (задиспозенный — `DISPOSED`), `_applied` не меняется, следующее
   изменение запускает снова (apply с тем же значением повторится; после ошибки compute
   пересчитывается при следующей проверке, даже без изменения deps — правка 6). Чтение
   memo, держащей ошибку, бросает внутри compute эффекта — это ошибка compute эффекта, если
   он её не поймал. Остальные run'ы
   дрена выполняются; дети, ожидавшие этот узел, перепланируются.

Своя сравнивалка результата — `createMemo(fn, { equals })` в compute-половине;
`options.equals` у эффектов нет. Компилятор для `style`/`classList` возвращает новый
объект при каждом пересчёте → apply на каждый пересчёт источника; per-property дифф в
applier'е делает это безвредным (Solid 2.0 живёт так же).

#### Кадровые планировщики — батчирующие очереди

`frameMeasure`, `frameMutation`, `frameForcedReflow` — не прямые `requestMeasure(run)`,
а обёртки над **тремя очередями run'ов** в ядре:

```
frameMutation(run, node):
  mutationRuns.push({ run, node })
  if (!mutationTaskScheduled) requestMutation(drainMutation)   // одна задача на фазу на кадр

drainMutation():
  snapshot = { global blocking, per-scope blocking }   // один раз на дрен
  for (i = 0; i < mutationRuns.length; i++)             // живой массив: добавленные
    { run, node } = mutationRuns[i]                     //   в ходе дрена выполняются в этом же дрене
    if (node disposed) continue
    scope = firstBlockingScope(node._scope, snapshot)   // цепочка scope → parent → … → root
    if (scope) { scope.parked.push(entry); ensureRelease(scope); continue }
    run()
  mutationRuns = []                                      // guard: эффект запущен 100 раз за дрен → цикл, перенос на кадр
```

Следствия (это то, что раньше спека приписывала «фаза = планировщик», но что в
реальности даёт только батчирование):

| Ситуация | Что происходит |
|---|---|
| N эффектов загрязнены одной записью | один rAF, одна задача на фазу, порядок — порядок постановки |
| mutate-эффект загрязнён из compute в mutate-фазе (`mapArray` пишет `item`/`index`-сигналы внутри compute `insert`'а) | **этот же** дрен — текст сообщения обновляется в том же кадре, что и перестановка |
| mutate-эффект загрязнён из mutate-applier | этот же дрен (guard защищает от циклов) |
| mutate-эффект загрязнён из measure-applier | mutate-фаза этого же кадра |
| measure-эффект загрязнён из mutate-applier | следующий кадр; в dev — предупреждение «measure-эффект X загрязнён из mutate-фазы — уедет на кадр» |
| нужно measure после mutate в том же кадре | `frameForcedReflow` |
| mutate-эффект загрязнён из forced-reflow applier (FLIP: mutate → измерение → mutate) | forced-reflow mutate-фаза **этого же** кадра (и в `flushSync`) |
| applier №3 начал blocking-анимацию | №4…N **выполняются** — гейт сэмплирован на входе в дрен; кадр атомарен |
| родитель пересоздал поддерево | дети задиспозены до своих `run` → пропускаются |

**Гейтинг и релиз.** Blocking-анимация (глобальная = корневой scope, или scope
узла по цепочке) паркует run в `scope.parked` — порядок сохраняется. На scope
регистрируется **одна** `once`-подписка на `isBlockingAnimating`; при релизе она
делает `requestMeasure(() => { re-enqueue parked в frameMeasure/frameMutation })`:
все отложенные run'ы попадают в **один следующий кадр в порядке фаз**, а не
выполняются синхронно в `transitionend`. Задиспозенные за время парковки узлы
отбрасываются при релизе. `tickEnd`- и `idle`-run'ы не гейтятся (логика не должна
ждать анимацию; idle и так её ждёт).

Отличие от teact: teact замораживает **всё** на blocking-анимации, включая
`setState`. У нас запись в сигнал проходит мгновенно (значение видно синхронно,
например в обработчике), а откладывается только кадровая работа.

Порядок внутри очереди — порядок постановки, который равен порядку уведомления
(pre-order DFS по спискам подписчиков). Подписчик встаёт в список зависимости по завершении
первого чтения в прогоне (связи — двусвязные списки, как в alien-signals), повторный прогон
сохраняет его место, отписка не переставляет остальных. Это **не** гарантия «родитель раньше
ребёнка» (ребёнок, прочитавший сигнал раньше родителя, стоит раньше). Ничто в дизайне на этот
порядок не полагается: атомарность поддерева даёт синхронный первый apply, пересоздание —
правило «предок не CLEAN → выход».

#### Остальное API core

- `createSignal(value, { equals? })` → `[get, set]` — сигнал не регистрируется у текущего owner'а
  (как в Solid): сигнал переживает dispose своего владельца; подписчики отцепляются при своём
  dispose. Memo и эффекты владеются как раньше. `createMemo(fn, { equals? })`;
  `createRoot(fn)`; `onCleanup(fn)`; `untrack`; `peek`; `getOwner`; `runWithOwner`;
  `onError`.
- `createContext(default)` / `useContext(ctx)` поверх `setContext`/`getContext`.
- `createSelector` — из maverick как есть.
- `mapArray(list, mapFn, { keyed })`:
  - `keyed: true` (по ссылке) — `computedKeyedMap`; `keyed: false` (по индексу) —
    `computedMap`;
  - `keyed: (item) => key` — дифф по ключу, `mapFn(item: Accessor, index: Accessor)`.
    Обязательно для иммутабельных данных telegram-tt (объект сообщения
    пересоздаётся при каждом изменении, строка обновляется на месте). Дубликат ключа
    → dev-warning и fallback на индекс (как `key` в teact); смена ключа у того же
    объекта = remove + create. `mapArray` держит копию предыдущего массива до
    следующего пересчёта — ожидаемо.
  - массив стора (§3.5): `mapArray` читает у списка ключ `$TRACK` — одна подписка на форму
    массива и обычный массив прокси элементов; изменение содержимого элемента до списка не
    доходит, его получает только строка.
- `flushSync()` — см. §3.1; дополнительно дренирует `tickEnd`-очередь.
- **`tickEnd` — один дрен до пустоты.** `flushTickEnd` крутит очередь, пока она не
  опустеет: колбэки, добавленные во время дрена (эффект → запись → эффект…), выполняются
  в нём же, без новых микротасков. Каскад завершается до любого микротаска, поставленного
  после записи.
- `batch` не нужен: эффекты и так ждут планировщика.

#### heavyAnimation: scope'ы и комбинатор

Порт `teact/src/teact/heavyAnimation.ts`, обобщённый до **scope'ов**:

```ts
const scope = createHeavyAnimationScope(parent?)
// { begin(duration = 1000, isBlocking = false): onEnd,
//   isAnimating: Signal<boolean>, isBlockingAnimating: Signal<boolean>,   // оба с .once
//   parent }

// глобальный API — это корневой scope
beginHeavyAnimation(duration?, isBlocking?)  = rootScope.begin
getIsHeavyAnimating / getIsBlockingAnimating = rootScope.isAnimating / .isBlockingAnimating
onHeavyAnimation(onStart, onEnd, scope = rootScope)   // замена хука useHeavyAnimation
onFullyIdle(cb, scope = rootScope)                    // через once, не опрос каждый кадр
```

Счётчики, авто-таймаут, идемпотентный `onEnd` — как в teact, на каждый scope.

**Per-subtree.** `<HeavyAnimationScope scope={scope}>` кладёт scope в context. При
создании эффекта ядро снимает ближайший scope из context в поле `node._scope`
(не хранит в `_context` каждого узла). Scope снимается **при создании**: дешевле,
и эффект не может «переехать». Проверка при дрене — по цепочке `scope.parent`.
Вложенный scope ждёт и внешний.

**Scope гейтит обновления, не создание.** Родительский `insert`, переключившийся
на `<HeavyAnimationScope><MessageList/></HeavyAnimationScope>`, создаёт список в
своём compute — в том же кадре, где начинается анимация. Для тяжёлых поддеревьев
штатный паттерн — `deferUntilIdle(scope, () => <MessageList/>, placeholder)`:
первый compute идёт через `createIdleEffect` этого scope, на время анимации стоит
плейсхолдер. (tt делает то же руками через `isReady`.)

**Non-blocking — комбинатор над планировщиком:**

```ts
gateOnHeavyAnimation(schedule, { blocking = false } = {}): Schedule
// (run, node) => анимация активна в цепочке node._scope
//                  ? scope.isAnimating.once(() => schedule(run, node))
//                  : schedule(run, node)
```

Кадровые очереди сами гейтятся только на blocking. Ждать и non-blocking — явный
opt-in. Стор гейтит DOM-эффекты парковкой по причине (§3.5).

### 3.3 `dom` — рантайм

Контракт задаёт компилятор: набор импортов из `moduleName`. Полный список фиксируется
acceptance-тестом (§5); ожидаемый состав: `template`, `insert`, `effect`, `memo`,
`createComponent`, `spread`, `assign`, `mergeProps`, `setAttribute`, `setAttributeNS`,
`setProperty`, `className`, `style`, `setStyleProperty`, `addEvent`, `delegateEvents`,
`ref`/`applyRef`, `use`, `readShallow`, `Portal`, `Dynamic`, `For`, `Show`, `Switch`,
`Match`.

База — `dom-expressions` 1.x `client.js`, с изменениями:

- `effect(compute, apply, options?)` → `createRenderEffect`; `options.name` от
  компилятора (`sourceNames.bindings`: `span.textContent`, `div.class:active`) кладётся
  в `node._name` (dev). `createComponent(Comp, props, name)` — имя на owner.
- `insert(parent, accessor, marker, init, options?)`: compute = `normalize(accessor())`
  (создание поддеревьев — чистый JS над detached DOM), apply = `insertExpression`.
  Дифф массивов — `reconcileArrays` из dom-expressions.
- **Классы.** Все пути записи класса (`class=` через `setAttribute("class")`,
  `className(el, obj)`, `classList`) идут через **дифф токенов** с `prev` на элементе:
  только `classList.add/remove` изменившихся. Императивные классы переживают
  реактивные обновления без реестра. `className=` на intrinsic-элементах у
  компилятора 2.0 — обычный атрибут → `console.error` «используй `class`», но значение
  всё равно применяется через дифф токенов (фикстуры компилятора должны работать).
- **Стили.** Объектная форма — per-property дифф; строковая — `cssText`. Extra-стили
  (`setExtraStyles`) хранятся в реестре на элементе и повторно применяются после каждой записи
  `cssText` — паритет с `updateStyle` teact (план 6); реестр накапливается между вызовами, `null`
  удаляет.
- **Безопасность записи атрибутов.** Рантайм не отправляет строку в HTML-приёмник, кроме
  статического HTML `template()` и явно названных `innerHTML` / `textContent` / `prop:srcdoc`.
  `setAttribute` (в него компилятор опускает `attr:`, `bool:`, spread и голые атрибуты)
  проверяет каждую запись, имена — без учёта регистра (`HREF`, `formAction`, `ONCLICK`),
  значения — после приведения к строке один раз (`URL`, `String`, объект с `toString`):
  - `on*` (`onclick`, в том числе через `attr:`): отказ для любого значения, кроме
    `null`/`undefined`/`false` (удаление). Обработчики задаются только через `onClick={fn}`.
  - URL-атрибуты (`href`, `src`, `action`, `formaction`, `xlink:href`, `poster`, `srcset`,
    `data`, `background`, `codebase`, `manifest`, `longdesc`, `cite`, `ping`): `javascript:`
    и `vbscript:` отклоняются везде; `data:` допускается на любом URL-атрибуте только
    для MIME `image/`, `audio/`, `video/` (встроенные картинки SVG `<image href>`,
    иконки `<link rel=icon>`, `<img src>`), любой другой MIME `data:` (`text/html` и т.д.)
    отклоняется; остальные схемы (http, https, mailto, tel, blob, относительные, свои
    вроде `tg:`) разрешены. `data:image/svg+xml` в `<iframe src>`/`<embed src>` тоже
    разрешён: такой документ получает opaque origin без доступа к приложению, то есть
    ровно то же, что и `src="https://чужой-сайт"`, а его фильтр схем не запретит; для
    недоверенных фреймов нужны `sandbox` и CSP `frame-src`/`object-src`. Исключение:
    `data:` на `src` элемента `<script>` отклоняется при любом MIME. Вообще `<script src>`
    с недоверенным значением небезопасен при любой схеме (подойдёт и `https://чужой-сайт`),
    защищает там CSP (`script-src`), а не фильтр схем. Для `<a download href>` с экспортом
    (CSV и т.п.) вместо `data:text/csv…` используйте `blob:` через `URL.createObjectURL`.
    Перед проверкой
    снимаются C0-символы и ведущие пробелы, схема приводится к
    нижнему регистру (как это делает парсер URL). В SVG-анимации (`to`, `from`, `by`,
    `values`) `javascript:`/`vbscript:` отклоняются всегда.
  - `srcdoc` — HTML-приёмник, как `innerHTML`: через `setAttribute` отклоняется (DEV
    `console.error`); осознанная запись — `prop:srcdoc={html}` (только доверенный HTML).
  - Что рантайм не контролирует: `prop:*` (в том числе `prop:href` и всё, что компилятор
    опускает в прямую запись свойства), `innerHTML=`, `setProperty`, *ключи* spread-объекта
    (`innerHTML`, `prop:*`, `use:*`), строковый `component` у `Dynamic` и `<script src>` с
    недоверенным значением (там помогает только CSP). Не подставляйте туда недоверенные
    значения и ключи. В типах JSX у `<iframe>` нет `srcdoc` (рантайм всегда отклоняет),
    типизирован только `prop:srcdoc`.
  - **DOM clobbering** переживает весь рантайм, не только делегирование. `<form>` имеет
    `[LegacyOverrideBuiltIns]`: listed-контрол (`input`, `button`, `select`, `textarea`,
    `fieldset`, `object`, `output`, в том числе связанный с формой через `form=` издалека) или
    `<img>` с `id="X"` либо `name="X"` затеняет даже встроенное свойство `X` самой формы
    (`form.parentNode`, `form.remove`, `form.insertBefore`, `form.nodeName`,
    `form.textContent`); `<div id>` и `<span name>` не затеняют (проверено в Chrome). Поэтому
    реконсайлер, `insert`, `render`, `Portal`, `spread`/`assign` и `setAttribute` читают
    структуру и вызывают методы DOM через нативы прототипов (`src/dom/natives.ts`:
    `parentNode`/`firstChild`/`nextSibling`/`nodeType`/`nodeName`/`localName`/`namespaceURI`/
    `ownerDocument`, `insertBefore`/`appendChild`/`replaceChild`/`removeChild`, сеттер
    `textContent`, `setAttribute`/`removeAttribute` и NS-варианты). Строка-форма с
    `<img id="remove">` не замораживает список, `<form><input name="insertBefore">` как
    родитель слота рендерится, `render` в такую форму монтирует и размонтирует. Не покрыто:
    `classList`, `style`, `addEventListener`, `value` и прочие API формы, потомок которой носит
    ровно это имя. Такой случай ломается громко и локально: эффект биндинга бросает при каждом
    запуске (`_applied` не двигается, ошибка в консоли повторяется), и поскольку компилятор
    группирует динамические атрибуты элемента в один эффект, а `spread` применяет пропсы одним
    проходом, остальные пропсы того же эффекта или спреда тоже не применяются; другие элементы,
    список и кадр не затронуты (если выше нет `onError`/ErrorBoundary: он получает ошибку, и его
    fallback может заменить содержимое границы). Стоимость натива: методы через `.call` стоят как
    `node.method(…)`, геттеры в Chrome примерно в 1,7 раза медленнее инлайн-чтения свойства
    (+4,5 нс на чтение, около +5 мкс на проход reconcile по 1000 строк; jsdom реализует геттеры
    на JS и этого не показывает). jsdom named properties форм не реализует: тесты задают
    дескриптор сами (`test/helpers/clobber.ts`), один прогон в headless Chrome описан в плане 3
    как ручной шаг.
  - Делегирование событий переживает DOM clobbering (`<form><input name="parentNode">`,
    в том числе элементы, связанные с формой через `form=` издалека): без исключений,
    зависаний и перехвата всплытия чужим элементом. Структура читается через геттеры
    прототипов, портальный host принимается только как собственный accessor и только как
    Node вне поддерева (число переходов ограничено), обработчик — только функция или объект
    с `handleEvent`. `currentTarget`/`target` после диспетчеризации возвращаются к нативным
    значениям. Ограничение: пока компилятор кладёт обработчики в expando-свойства
    (`_$$click`, `_$$clickData`), listed-контрол формы или `<img>` с `id`/`name`, равным
    имени expando, затеняет его на этой форме. Форма узнаётся по `nodeName` в обоих регистрах
    (в XHTML-документе он нижнего регистра). Затенение распознаётся по дескриптору
    (named property формы — собственное **неперезаписываемое** свойство, expando рантайма
    всегда writable), поэтому обработчик с bound-данными, которые сами являются Node,
    по-прежнему вызывается; затенённый обработчик (или его данные) пропускается, предки
    отрабатывают, DEV `console.error` (в Chrome затенение побеждает при чтении, поэтому
    пропускается и обработчик, записанный до появления затеняющего потомка). Запись expando на
    такую форму бросает в strict mode — `addEvent` ловит это (DEV `console.error` называет
    ключ, на котором бросило), спред не обрывается. Инлайн-обработчики компилятор пишет
    напрямую (`el._$$click = fn`, мимо `addEvent`); это безопасно: запись идёт сразу после
    клона шаблона, до появления динамических id и детей, а последующее затенение ловит проверка
    дескриптора при диспетчеризации. Уровень `document` (у него
    тоже `[LegacyOverrideBuiltIns]`: `<img name="createTextNode">` в документе ломает создание текста
    в каждой новой строке, `name="body"` уводит `<Portal>` внутрь `<img>`) закрыт: рантайм вызывает
    `Document.prototype.createTextNode`/`createElement`/`createElementNS`/`importNode`,
    `EventTarget.prototype.addEventListener`/`removeEventListener` и геттеры `body`/`activeElement`
    через `natives` (`.call(document, …)`).
  - `Dynamic component={строка}` — граница доверия: имя тега это ключ, политика значений
    ему не помогает (`style`, `base`, `meta`, `link`, `iframe`, `object`, `embed` достижимы по
    имени), так что строка приходит только от автора, не из контента. Рантайм проверяет имя
    (`/^[a-zA-Z][a-zA-Z0-9-]*$/`; иначе ничего не рендерится, DEV `console.error`) и создаёт
    `script` инертным: клон `template('<script></script>')` несёт флаг already started,
    `createElement('script')` исполнил бы текст. (jsdom этот флаг у разобранных фрагментов не
    ставит, поэтому тест фиксирует путь создания, а не исполнение; в Chrome проверено.)
  - Директивы `value` и `checked` зарезервированы; `defineDirective` на занятое имя —
    DEV `console.error`, регистрация игнорируется.
- `render(code, el)`: `createRoot` → создать поддерево; первый apply корневого
  `insert` синхронный (§3.2), attach в attached-контейнер — через
  `forceMutation(cb, el)` stricterdom'а. Монтирование синхронное, `flushSync` не нужен.
  `Portal` — то же для своего mount-узла.

Хелперы для императивных анимаций (API-совместимость с teact):
`addExtraClass`, `removeExtraClass`, `toggleExtraClass`, `setExtraStyles` — тонкие
обёртки над `classList` / `style.setProperty`; stricterdom следит за фазой.

#### Контролируемые инпуты — директивы

Компилятор 2.0 для `<input value={s()}>` эмитит `_$effect(() => ({e: s(), …}),
({e}) => { _el$.value = e ?? "" })` — прямое присваивание, рантайм ничего не видит.
Поэтому контроль — явный примитив:

```tsx
<input use:value={text} onInput={e => setText(filter(e.currentTarget.value))} />
<input type="checkbox" use:checked={flag} onChange={…} />
```

Компилятор 2.0 **не эмитит `_$use`**: `use:value={text}` опускается в
`setAttribute(el, "use:value", text)` (аксессор передаётся невызванным), и так же —
`on:`, `oncapture:`, `attr:`, `bool:`, `class:`, `style:`, `classList` (проверено
компиляцией на rc.14). Поэтому `setAttribute` рантайма — **диспетчер по префиксу
имени**, а директивы — реестр по имени (`defineDirective`; `value`/`checked` встроены;
`use` по-прежнему экспортируется). `use:value` делает:

- `createMutationEffect(() => sig(), v => setValueKeepingCaret(el, v))` — applier
  пишет только если `el.value !== v`; восстанавливает каретку по snapshot'у.
- один **document-level** `input`/`change`-listener, зарегистрированный **после**
  `delegateEvents(['input'])` — только так он выполняется после делегированных
  пользовательских обработчиков (listener на элементе и микротаск сработали бы раньше):
  snapshot `selectionStart/End` (до любых записей этого тика), затем
  если `el.value !== sig()` — **синхронный** (в форме с аксессором; plain-форма — ниже) откат через ту же
  `setValueKeepingCaret` (как teact; `.value` не виден MutationObserver, кадра
  мерцания нет). Принятый ввод (`sig() === el.value`) не трогается; отформатированный
  (`sig()` ≠ ввод) применяется сразу, без ожидания кадра.
- во время composition (`e.isComposing`, `compositionstart…compositionend`) в `el.value`
  ничего не пишется, иначе ломается IME. При этом откат и программная запись — разные случаи:
  - **откат и форматирование ввода** во время composition не выполняются вообще;
  - **программная запись** (эффект доставил новое значение, например «Отправить» →
    `setText('')` во время слова, набираемого на Android-клавиатуре) не теряется, а
    откладывается. На `compositionend` применяется самое новое авторитетное значение
    (живой аксессор или последнее доставленное), и оно побеждает набранный текст. Проверка
    отката для этого `compositionend` пропускается. Если после программной записи обработчик
    принял ещё composing-ввод, новейшим значением станет он: поле и сигнал совпадут.
  - **проверка отката после `compositionend`** в обеих формах откладывается в mutate-фазу, а
    не выполняется синхронно. Обработчики с паттерном «пропускать `isComposing`» принимают
    зафиксированный текст в своём `compositionend` или в `input`, который некоторые движки
    шлют после `compositionend`. Оба срабатывают после document-listener'а, и синхронный откат
    стёр бы CJK-текст.
  - **явная запись насквозь — `forceControlledValue(el, value?)`** (экспорт `frameact/dom`).
    Нужна для «Отправить → очистить поле» на Android, где каждое слово — composition: отложенная
    программная запись применится только на `compositionend` и проиграет следующим буквам
    пользователя (если он продолжит то же слово, очистка теряется). Вызывать после того, как
    сигнал уже содержит значение (в plain-форме эффект компилятора ещё не доставил его, поэтому
    `value` передаётся явно). Что делает: пишет `el.value` **синхронно**; сбрасывает состояние
    composition и отложенную программную запись; запоминает значение как доставленное (откат и
    повторное применение не последуют); **отменяет composition** — сфокусированное поле во
    время composition получает `blur()` и `focus({ preventScroll: true })`, клавиатура остаётся
    на экране, каретка ставится в конец нового значения. Поздний `compositionend` отменённой
    composition текст не возвращает (ему достаётся только проверка авторитетного значения).
    `value` опущен — берётся текущее авторитетное значение (аксессор или последнее доставленное).
    На элементе без `use:value` просто пишет `el.value` (и предупреждает в DEV). Это
    исключение из правила «во время composition ничего не пишется»: пользоваться им только для
    явной команды пользователя, а не из обычных реактивных обновлений.
    - **Контракт вызова.** Только синхронно из обработчика пользовательского события (клик или
      Enter на «Отправить»), а не из apply эффекта: в mutate-фазе `focus()` форсирует layout, а без
      user activation iOS Safari и Android Chrome не вернут клавиатуру после повторного фокуса. Без
      активной composition это обычная запись, допустимая в любой фазе. В DEV при активной
      composition предупреждение (`console.warn`) выводится в mutate-фазе и при
      `navigator.userActivation.isActive === false`; в plain-форме без `value`, пока эффект
      компилятора не CLEAN, выводится `console.error` (записалось бы устаревшее значение).
    - **Окно перехвата.** На время blur → запись → focus `input` и `compositionend`, адресованные
      полю, останавливаются на document в capture-фазе (`stopImmediatePropagation`): коммит, который
      движок шлёт синхронно внутри `blur()`, не доходит ни до обработчиков приложения, ни до самой
      директивы. Окно вложенное (стек): обработчик `blur` приложения может вызвать force для другого
      поля. Если движок вернул старый текст внутри `focus()`, перед выходом значение дописывается
      заново, и дополнительно ставится отложенная проверка.
    - **`isForcingControlledValue(el?)`** (экспорт `frameact/dom`): `true`, пока идёт этот цикл
      (для `el`, если задан). Обработчики `blur`/`focusout`/`focus`/`focusin` приложения при этом
      **срабатывают** (`relatedTarget` равен null); флаг позволяет отличить синтетический цикл от
      настоящего ухода пользователя (сохранение черновика, «перестал печатать», закрытие подсказок).
    - **Остаточный риск.** Коммит, который движок доставляет асинхронно после возврата из
      `blur()`/`focus()` (Android IME работает через IPC), окно не покрывает: поздний
      `compositionend` ведёт к отложенной проверке и откату к авторитетному значению, а поздний
      `input` со старым текстом дойдёт до обработчика приложения. Нужна ручная проверка на
      устройствах: Android Chrome + Gboard (латиница и CJK), iOS Safari + японская kana, desktop
      Chrome/Firefox + Pinyin (текст очищается, следующая буква не воскрешает слово, клавиатура
      остаётся).

Три формы входа (по тому, что получает `setAttribute(el, 'use:value', x)`; `use:checked` —
по тем же правилам):

- **Аксессор под owner'ом** (`use:value={text}`) — директива создаёт свой mutation-effect.
  Его compute отдаёт свежий бокс `{ v }` на каждое изменение, чтобы applier всегда
  сравнивал с живым DOM, а не с последним применённым значением (иначе принятый ввод
  `'abc'` и программный `setText('ab')` в том же кадре оставили бы в DOM `'abc'`);
  document-level проверка читает живой аксессор.
- **Plain-значение** (`use:value={props.text()}`: компилятор оборачивает выражение в
  эффект и вызывает `setAttribute(el, 'use:value', v)`) — директива пишет значение той же
  caret-логикой. Живого аксессора для сверки в момент события нет (эффект компилятора ещё
  не доставил то, что только что записал обработчик), поэтому синхронно откатывать нельзя:
  откат принятого символа с повторным применением кадром позже даёт мерцание текста и
  каретки. Listener снимает snapshot каретки и ставит **одну проверку на кадр** (флаг
  `pending`, `requestMutation`) в mutate-фазу. Она выполняется после эффекта компилятора:
  делегированный `onInput` пишет сигнал первым, и mutate-работа эффекта попадает в очередь
  раньше, чем эта проверка. Если доставленное с момента события значение равно `el.value` —
  обработчик принял ввод, ничего не пишем; иначе восстанавливается последнее доставленное
  значение обычной caret-записью. Директива вызывается внутри apply эффекта компилятора и
  запоминает его узел: пока узел не CLEAN (dirty, в очереди или припаркован
  heavy-animation гейтингом), проверка ничего не откатывает — ожидающая доставка всё равно
  запишет авторитетное значение (для принятого ввода оно то же, записи не будет; для
  отклонённого после принятого — последнее принятое). Откат только при CLEAN-узле и
  расхождении; отклонённый ввод эффект не «пачкает», поэтому восстанавливается в следующем
  кадре и внутри гейтируемого поддерева. Синхронный откат остаётся только у форм с аксессором.
- **Аксессор внутри apply** эффекта (`use:value={props.text}`, где `props.text` сам
  функция: компилятор оборачивает это в `effect(() => props.text, v => setAttribute(el,
  'use:value', v))`) — у apply нет owner'а, поэтому директива эффект не создаёт: в DEV
  `console.error` с подсказкой «передай аксессор напрямую: `use:value={text}`, либо
  значение: `use:value={props.text()}`», один раз пишет `untrack(value)` (с обычной
  caret-логикой) и держит аксессор для проверки отката. Программные изменения в этом
  fallback не отслеживаются — об этом и сообщает ошибка.

**Известное ограничение: `<select use:value>` и поздно добавленные `<option>`.** Значение
применяется при доставке сигнала. Если нужная опция появляется позже (динамический список
`<For>`/`.map`, пришедший после значения), браузер уже выбрал другую опцию (первую), а
повторной доставки нет: DOM молча расходится с сигналом, пока сигнал не изменится. Компилятор
эмитит `insert` опций раньше `use:value`, поэтому опции, существующие к моменту первого
применения, проблемы не создают. Это то же поведение, что у Solid. Обходы: рендерить `<select>`
после загрузки опций, держать список опций стабильным или вызвать
`forceControlledValue(select)` (без `value`) после изменения списка: он применит текущее
авторитетное значение привязки. Правка рантайма (повторное применение последнего
доставленного значения при изменении `childList` у `<select>`) вынесена в бэклог.

Реактивный `value=`/`checked=` на `INPUT/TEXTAREA/SELECT` рантайм увидеть не может
(прямое присваивание) → предупреждение «используй `use:value`» выдаёт **lint по исходнику
в Vite-плагине**. `selectionStart/End` добавляются в `layoutCauses` stricterdom'а:
читать их можно только в measure-фазе (обработчик события — measure).

#### Списки

- `<For each keyed fallback>` — `mapArray` + `insertExpression` (LIS-дифф).
- `<For each order="manual" orderKey={item => …}>` — порт идеи `renderFastListChildren`
  для случаев, когда визуальный порядок задаётся `transform`'ом по `index()`, а
  DOM-порядок должен оставаться стабильным (ChatList). Контракт:
  - `For` в этом режиме **владеет порядком своего DOM-диапазона**: сохранённые узлы
    **не двигает**, кроме тех, у кого изменился `orderKey`; новые строки вставляет на их
    индекс в списке (в начало, в конец или между сохранёнными узлами — пачкой);
  - наружу `insert`'у возвращает массив узлов в **DOM-порядке**, а не в порядке
    списка, с пометкой «ручной порядок»; `insertExpression` применяет такой массив
    собственным insert-only реконсилером (`reconcileManual`), а не `reconcileArrays`
    (udomdiff заменяет и перевставляет сохранённые узлы): он удаляет ушедшие узлы,
    вставляет новые пачкой перед одним якорем (следующий сохранённый узел или маркер)
    и ровно один раз двигает строки со сменившимся `orderKey` — сохранённых не
    касается вовсе;
  - `orderKey(item)` вычисляется в compute `For` без трекинга и хранится per key между
    пересчётами; сам по себе не реактивен — перестановка происходит при следующем
    пересчёте списка. `For` трекает `each()`, поэтому замена элемента на другой с иным
    `orderKey` на той же позиции — тоже пересчёт, и строка переезжает на свой индекс;
  - `DocumentFragment` не нужен: `For` не пишет в DOM из compute, а `reconcileManual`
    позиционирует узлы относительно слота (якорь — следующий сохранённый узел или
    маркер), не по `childNodes[i]`; поэтому dev-assert «единственный ребёнок, без
    fallback» снят как ненужный, `fallback` разрешён. `For` должен быть единственным
    содержимым своего слота: внутри большего массива метка теряется (dev-предупреждение)
    и применяется обычный `reconcileArrays`.

### 3.4 `stricterdom`

Порт `teact/src/lib/fasterdom/stricterdom.ts` и `layoutCauses.ts`: патч
геттеров/методов, вызывающих layout → ошибка, если `phase !== 'measure'`;
`MutationObserver` на `document.body` → ошибка, если мутация при `phase !== 'mutate'`.
Detached-узлы игнорируются (`document.contains`), поэтому создание поддеревьев
нарушением не считается. `data-*` и `contentEditable` исключены. `forceMeasure`,
`forceMutation`, `suppressStrict`, `setHandler` — как в teact. Включается в dev
(`enableStrict()`). `layoutCauses` дополняется `selectionStart/selectionEnd`.

**Атрибуция.** Ядро в dev держит `currentEffect` на время `run`. Обработчик по
умолчанию дополняет ошибку путём: `Message > MessageMeta > span.textContent [mutate]`
(имена компонентов — третий аргумент `createComponent`, имена биндингов —
`sourceNames.bindings`, фаза — планировщик эффекта, scope — если есть). Туда же:
«slow run» (> 7 мс) с тем же путём и предупреждение «measure-эффект загрязнён из
mutate-фазы».

Следствие архитектуры: поскольку **все** записи в живой DOM идут через mutate-фазу,
любая точка вне её — безопасное окно для чтения layout. В teact это соглашение, у
нас — проверяемый инвариант с именем нарушителя.

### 3.5 `store` — глобальный стор на сигналах

**Модель B — дерево сигналов (signal-way).** Состояние — дерево простых объектов и массивов. Каждое
свойство лениво становится сигналом при первом **отслеживаемом** чтении. Чтение
`state.chats[id].title` подписывает ровно на этот путь, запись по пути уведомляет только этот лист.
Иммутабельные данные с сервера вливаются диффом по ключу (`reconcile`). Производные — обычные
`createMemo`/`createSelector`, экшены — обычные функции. Первая редакция (порт модели teact: иммутабельный
`global`, `mapStateToProps`, bridge-сигнал на scope) и кандидат A (иммутабельный корень + селекторы)
отклонены. На fine-grained ядре они сводят точечную реактивность к пересчёту контейнеров или
селекторов и порождают швы между пропсами и устаревшим global. Модель проверена прототипом
(замеры — в блоке «Стоимость» ниже).

```ts
const [state, setState] = createStore<GlobalState>(INITIAL_STATE);   // state: DeepReadonly<GlobalState>
setState('chats', id, 'title', title);                     // путь: ключ | ключи[] | (item, i) => boolean
setState('chats', id, 'unread', (n) => n + 1);             // апдейтер
setState('chats', id, chat);                               // значение в конце пути заменяет
setState('chats', id, merge({ title, unread: 0 }));        // слияние — только явно
setState('drafts', chatId, undefined);                     // undefined удаляет ключ
setState('chats', id, produce((c) => { c.title = t; c.unread++; }));   // драфт
setState('messages', chatId, reconcile(chunk, { key: 'id' }));        // данные с сервера
unwrap(state.chats[id]);   // живое сырое дерево, O(1)
snapshot(state);           // отвязанная глубокая копия
live(() => state.typing);  // обход гейта на чтении
ungated(() => setState(…));// обход гейта на записи (forceOnHeavyAnimation)
const actions = defineActions({ openChat(id: string) { … } });   afterActions(cb);
```

**Хранение.** На каждый сырой объект, хоть раз прочитанный через прокси, есть узел: он и handler
прокси, и таблица слим-сигналов ядра по ключам, и сигнал формы (`self`). Связь «сырой объект → узел» —
`WeakMap`; на объекты пользователя ничего не пишется. Листья не принадлежат owner'у, как
`createSignal`. Неотслеживаемое чтение листьев не создаёт. Запись `setProperty(raw, key, v)` пишет в
сырой объект и уведомляет только существующие сигналы: лист, `length` (при усечении — удалённые
индексы) и форму (у массивов — любая запись индекса или длины, у объектов — добавление или удаление
ключа). Прокси только для чтения: запись в неё бросает `TypeError`.

**Зафиксированные требования и оптимизации**

1. **Чтение стоит O(изменённых подписок), а не O(подписчиков).** Подписка — на лист пути
   (`state.chats[id].title`, `state.messages[c][i].content`). Запись уведомляет только читателей
   этого листа. Обновление одной строки из 1000 — один пересчёт строки, без `mapStateToProps` × n и
   `shallowEqual` (замер: 0.55 мкс против 7.3 мкс у `For keyed` + `item()`).
2. **Флаг «выбран/текущий» — O(1).** Через `createSelector` ядра над листом стора: смена текущего id
   пересчитывает две строки.
3. **Запись по пути без копий.** *Изменено против кандидатов:* в B запись по пути мутирует сырой
   объект на месте и ничего не копирует, без лестницы spread'ов. Идентичность сохраняется у всех
   веток, изменённых тоже: у прокси (одна на сырой объект), у сырых объектов, у строк `For`. Дифф по
   ссылкам заменён подписками на листья. `reconcile` отсекает `prev === next` и неизменённые
   примитивы без уведомлений. Снимок не бесплатный: `snapshot()` — глубокая копия, `unwrap()` — живое
   дерево; копирование при записи после снимка (снимок за O(1)) — только если покажут замеры. Причина: копирование пути (как в tt сейчас) стоило бы копии `byId` на каждую правку
   сообщения и ничего не давало бы UI. Без внешних зависимостей.
4. **Асинхронный код не держит снимок.** Состояние — живая прокси: после `await` чтение даёт текущее.
   Через `await` держать id, а не прокси объекта. Объект, заменённый целиком (а не слитый через
   `reconcile`), остаётся у старой прокси. Отдельная dev-проверка «устаревшего global» не нужна.
5. **Экшены — обычные типизированные функции.** `defineActions(defs)` выводит типы из определения,
   без строкового реестра. Вложенный вызов ставится в очередь и выполняется после текущего экшена
   (FIFO). `afterActions(cb)` — после каскада. Ошибка или отклонение экшена логируется, очередь
   продолжается. Синхронный экшен возвращает `void`; `async`-экшен — `Promise<void>`, который
   резолвится после завершения и никогда не реджектится.
6. **Гейтинг heavy-animation — парковка по причине.** *Уточнено.* Запуск эффекта, причина которого —
   только запись в стор, ждёт конца анимации (blocking или non-blocking) в цепочке scope'ов эффекта.
   Запуск по любой другой причине (локальный сигнал, memo, изменившаяся не из-за стора, `live`,
   `ungated`, run потомка) выполняется сразу и читает **текущий** стор целиком. Ни одно вычисление
   не видит два момента стора. Механика:
   - store-walk помечает то, что загрязняет (CLEAN → грязное), битом `F_STORE`. Обычный walk,
     дойдя до узла с `F_STORE`, снимает бит и спускается ниже, даже если узел уже грязный.
     Запись результата memo, пересчитанной только из-за стора, — тоже store-walk;
   - решение принимается при выполнении run'а (`runEffect`), **одно на дрен**: scope считается
     анимирующим для дрена, если анимирует сейчас **и** начал анимацию до открытия дрена (эпоха
     начала). Applier, начавший анимацию посреди дрена, кадр не делит; scope, закончивший анимацию
     посреди дрена, не считается, и цепочка проверяется дальше (внутренний закончил — внешний ещё
     держит). Запись до старта анимации с run'ом после старта паркуется, как `runCallbacks` в teact
     на tickEnd;
   - запаркованный эффект остаётся грязным (CHECK/DIRTY), run не бронируется. Повторные записи
     схлопываются. Обычный walk распарковывает эффект. Обычный run потомка распарковывает
     запаркованного предка-эффекта и выполняется после него (правило предка §3.2);
   - на release scope'а запаркованные эффекты бронируются в порядке парковки и попадают в
     следующий кадр. Если вложенный scope ещё анимирует, эффект паркуется там снова. Соседние
     поддеревья не ждут;
   - гейтятся DOM-эффекты с `F_STORE` (render/mutation/measure) и эффекты, явно обёрнутые в
     `gateOnHeavyAnimation`. Логика на tickEnd (сеть, сохранение, колбэки) **не** гейтится: ей незачем
     стоять во время анимации. Глобальная анимация (корневой scope) паркует весь UI над стором.
     Обработчики событий и императивные чтения видят текущее состояние: чтения никогда не гейтятся;
   - обходы — фасады с заметными именами, а не опции: `live(() => …)` (читающее вычисление не
     паркуется; live-memo передаётся обычному walk'у) и `ungated(() => setState(…))`;
   - dev-таймер «Slow store update» (> 7 мс) на каскад экшенов.

   Почему не «версионные листья» (чтение внутри scope'а возвращает значение на старт анимации):
   memo, созданная вне scope'а, вычисляется вживую, и эффект видит состояние, которого у стора не
   было (рваное чтение; тест прототипа). Записи при этом всё равно будят эффекты внутри анимации,
   так что работа не экономится. Цена выбранного варианта: биты причины в `notify`/`update` (+1…4 %
   на обычных сигналах); на пути чтения кода гейта нет.

   Видимое расхождение, пока эффект запаркован. Строка списка может перезапуститься по обычной
   причине: правило зомби-строк (§3.2) тянет map-memo перед её run'ом, а запись `item`/`index`
   оставшимся строкам — обычный walk. Допустим, элемент удалён записью в стор, а затем сработал
   обычный сигнал (hover): строки перезапускаются и показывают **новые** `index()`, а запаркованный
   эффект списка до конца анимации показывает прежний порядок. Это следует букве правила: запуск по
   другой причине выполняется сразу и читает текущее состояние. Согласованность гарантируется
   внутри одного вычисления, а не между запаркованным эффектом и строками, уже обновлёнными по
   другой причине.
7. **Поле ввода.** *Изменено.* Эффекты `use:value`/`use:checked` никогда не паркуются: эффект
   директивы помечен live, доставляющий эффект компилятора в plain-форме закреплён (вместе со своим
   сгруппированным эффектом). Поэтому `use:value`, привязанный к стору напрямую, работает в обеих
   формах и во время анимации. Синхронная проверка отката видит запись, программная очистка
   доставляется сразу, отклонённый символ восстанавливается. Фасад для инпутов не нужен. Паттерн
   «локальный сигнал + экшен по blur/debounce» остаётся допустимым, но больше не обязателен.
8. **Никаких служебных полей и копий объектов пользователя.** Узлы — в `WeakMap`. `toEqual` и
   `JSON.stringify` работают на прокси одинаково в dev и prod. `structuredClone(прокси)` бросает
   (Proxy не клонируется) тоже одинаково: для клонирования есть `snapshot()`/`unwrap()`. Стор владеет
   объектами, которые держит, и мутирует их, включая принятые `reconcile`. Запись в замороженный
   объект — ошибка в DEV.
9. **Ошибки изолированы.** Бросившая memo над стором держит ошибку и восстанавливается на следующей
   записи (`onError` читателя, прежнее значение сохраняется). Бросивший экшен не останавливает
   очередь.
10. **Списки.** *Уточнено.* Элемент массива стора — стабильная прокси. Рекомендуемый паттерн —
    `For each={state.list}` с режимом по умолчанию (по ссылке). Ключ `$TRACK` подписывает `mapArray`
    на форму массива одной связью и отдаёт обычный массив прокси, собранный из сырого массива в
    обход ловушек. Изменение содержимого элемента будит только его строку. `keyed: fn` и `item()` —
    для внешних иммутабельных массивов. Список id с поиском сущности (`state.chats[id]`) допустим
    благодаря правилу ядра: run строки сначала тянет грязную memo своего `mapArray` (внутренний скоуп
    строк знает свою memo), так что строка удалённой сущности диспозится, а не выполняется. Бенч §5
    сравнивает с «подпиской на строке».

**Семантика записи.** Значение в конце пути **заменяет** прежнее; слияние объектов — только явным
`merge()`. `undefined` в конце пути **удаляет** ключ (проверки через `in` и `Object.keys` честные);
по индексу массива форма пути бросает `TypeError` (`produce(a => a.splice(i, 1))` удаляет элемент),
внутри `produce` — семантика JS (`draft[i] = undefined` хранит значение, `delete draft[i]` — дыра),
`reconcile` пишет явный `undefined`-элемент как значение. Корень не заменяется: только `merge`,
`produce`, `reconcile`. Объект, записанный в стор (спред прокси, `merge({ y: state.a.b })`),
усыновляется — разворачивается вглубь, в сыром дереве прокси не бывает. Лист удалённого ключа
удаляется из таблицы после уведомления (листья `in` для отсутствующих ключей остаются).
Замороженный объект — неизменяемое **значение**: не оборачивается, читается сырым, заменяется
целиком; замороженный корень — `TypeError`; `produce` на замороженном — `TypeError` в DEV; запись в
него — в DEV `TypeError` с понятным сообщением, в проде нативный `TypeError` strict mode.
Ограничения: `Object.hasOwn`/`hasOwnProperty` не реактивны (реактивная проверка — `in`); геттер на
сыром объекте вызывается с сырым receiver'ом и не трекается (производные — `createMemo`); `undefined`
тайпчекается и для обязательных ключей; дубли ключа в `reconcile` кладут один сырой объект на два
индекса (ключи должны быть уникальны); один сырой объект по двум путям — одни и те же листья.

**Обход и память.** Прокси отдаёт литеральные дескрипторы данных (без замыкания на ключ), но
обход через `Object.keys/values/entries`, spread и `for…in` всё равно в разы медленнее обычного
объекта; для больших словарей — `keys(obj)`/`values(obj)`/`entries(obj)` из `frameact/store`: они читают
сырой объект и подписываются один раз (`keys` — на форму, `values`/`entries` — на любую запись в
объект); DEV-предупреждение при обходе прокси с более чем 1000 ключей. Мутаторы массива в `produce`
(`push`/`pop`/`shift`/`unshift`/`splice`/`sort`/`reverse`/`fill`/`copyWithin`) и перезапись порядка в
keyed-`reconcile` пишут в сырой массив нативно и уведомляют один раз (`length`, изменившиеся индексы с
читателями, форму). Лист (а также сигналы формы и значений), потерявший последнего подписчика,
удаляется из таблицы узла хуком отписки ядра (только для листьев стора); пустая таблица тоже: память
следует за тем, что подписано, а не за всем когда-либо отрисованным. Узел (`StoreNode` + прокси)
живёт, пока жив сырой объект: идентичность прокси — часть контракта (`For` по ссылке). Гейт кэширует
первую анимирующую цепочку scope'а на эпоху дрена.

**Ключи из данных.** Стор принимает серверный JSON, поэтому ключи из данных — граница доверия.
`__proto__` никогда не хранится: `JSON.parse` создаёт его как собственное свойство, `adopt` вырезает
его у новых объектов, `setProperty`/`merge`/`reconcile`/черновик `produce` его пропускают (DEV
`console.error`, в проде молча), чтение `state.x.__proto__` отдаёт `undefined`. `Object.prototype` и
`Array.prototype` (и прототипы встроенных классов) не оборачиваются (`isWrappable`); путь `setState`
спускается только по собственным свойствам (`TypeError` «nothing to descend into»);
`reconcile` обходит только собственные ключи. Имена членов `Object.prototype` (`constructor`,
`toString`…) — обычные ключи словаря: добавление такого ключа уведомляет читателей `Object.keys`/`in`/
чтения, а чтение ещё не созданного ключа подписывает на форму объекта. Класс/стиль-привязки DOM
обходят только собственные ключи. `produce`: черновик живёт только внутри колбэка (запись после
возврата — `TypeError` в DEV, в проде отбрасывается), `produce` на не-обычном объекте — `TypeError`;
read-only вид отвергает `setPrototypeOf`/`preventExtensions`. Индекс массива за `length` в пути
`setState` — `TypeError`, как и дыра. Части пути — только строка, число или символ (иначе `TypeError`: массив или
объект с `toString` приводился бы к `"__proto__"` мимо проверки). Fan-out проверяется сухим проходом до первой
записи: спуск (отсутствующий ребёнок), индексы и дыры. Updater'ы (`merge`, `produce`, свои) сухим проходом не
проверяются: `setState('chats', ['a', 'b'], merge({…}))`, где `chats.b` — примитив, уже слил `a`, когда `b`
бросает. Черновик `produce` валиден только в своём вызове (черновик другого `produce` не пишет, пока идёт
этот); `keys`/`values`/`entries` работают и на черновике (без подписки, элементы — черновики).

**Требования к ядру** (дополняют §3.2): флаги `F_STORE`/`F_PARKED`/`F_LIVE`/`F_LIVE_PIN`;
`writeStoreNode`; тип walk'а при записи результата memo; спуск обычного walk'а через узлы с
`F_STORE`; relay live-узлов; хук стора в начале `runEffect`; распарковка предка в правиле предка;
сэмплинг scope'ов на дрен (`openGateSample` в кадровых дренах; tickEnd-эффекты не гейтятся и
сэмпл не открывают; исключение — `gateOnHeavyAnimation(tickEnd)`: он помечен store-gated и решает
по живому состоянию scope'ов, без эпохи дрена); релиз запаркованного множества идёт через
measure-задачу (как релиз blocking-парковки), так что множество целиком попадает в следующий кадр,
measure раньше mutate, даже если анимация закончилась в mutate-фазе; счётчик анимирующих scope'ов;
`$TRACK` в `mapArray`; ссылка «скоуп строк → memo `mapArray`» в правиле предка.

**Стоимость (замер прототипа, прод-сборка, M1 Pro).** Чтение листа — 33 нс (против 11 нс у `item()`).
Подписанный лист — 192 Б (против 320 у `createSignal` со связью). Строка дороже на ~150 Б, чем
`For keyed` + `item()`. Первый рендер 1000 строк дороже на 2–9 %. Правка одной строки из 1000 дешевле
в 5–13 раз. `reconcile` 1000 сообщений — 0.56 мс; в DOM при 10 изменённых пересчитываются 10
привязок, а не 1000.

## 5. Тестирование

**Юнит (vitest + jsdom).** Кадр — через `flushSync()`; цепочки через микротаски —
`await flushMicrotasks()`, не fake timers.

- core: алмаз без глитчей; динамические зависимости; dispose поддерева; запись в
  собственный источник во время compute не теряется (правка 2, latch); `mapArray` по
  ключу — обновление строки на месте при смене ссылки, перестановки, удаления,
  дубликат ключа → warning + индекс, смена ключа = remove + create.
- effects: first-run — mutation синхронно, measure/tickEnd/idle через планировщик;
  **measure-эффект, созданный внутри insert-compute, впервые выполняется после attach
  и видит ненулевой layout**; `run` при не-CLEAN предке выходит, предок пересоздаёт
  поддерево один раз; `_applied` даёт корректный `prev` после пересоздания; запись
  из measure-applier → mutate того же кадра; из compute в mutate-дрене → тот же
  дрен; measure из mutate-applier → следующий кадр + dev-warning; guard на цикл;
  два канала cleanup — apply-cleanup не выполняется, если apply не последовал;
  dispose вне mutate откладывает apply-cleanup в mutate; ошибка в apply не
  прерывает дрен, узел CLEAN.
- scheduler: порядок четырёх очередей; throttling; таймаут-фолбэк; `flushSync`
  с реентером → ошибка; сырые задачи, добавленные в ходе фазы, → следующий кадр.
- heavyAnimation: blocking паркует весь дрен атомарно (applier, начавший анимацию,
  не прерывает текущий кадр); релиз — один следующий кадр, measure раньше mutate, в
  исходном порядке; одна `once` на scope; задиспозенные при релизе отброшены;
  `begin` внутри релиза не зацикливает; non-blocking не влияет на кадровые очереди,
  влияет на `gateOnHeavyAnimation`; scope: эффект внутри ждёт, соседний нет,
  вложенный ждёт внешний; `gateOnHeavyAnimation` на уровне модуля видит scope узла;
  `deferUntilIdle` откладывает первый compute.
- store: подписка на лист — запись уведомляет только его читателей; `reconcile` с 10 изменёнными
  из 1000 уведомляет 10; замена/`merge`/`undefined` удаляет ключ; `produce`; `snapshot`/`unwrap`;
  парковка по причине: эффект, грязный только из-за стора, ждёт анимации своего scope, соседний нет,
  локальный сигнал не ждёт и читает текущий стор, нет рваного чтения, release перезапускает ровно
  запаркованные, повторные записи схлопываются; tickEnd-логика не гейтится; `live`/`ungated`;
  `use:value` на сторе не откатывает принятый ввод во время анимации; строка удалённой сущности
  диспозится, а не выполняется (зомби-строки); экшены: FIFO вложенных, `afterActions`, ошибка не
  останавливает очередь; фазз гейта.
- dom: дифф токенов класса сохраняет императивные на всех путях записи; `style`-объект
  per-property; `use:value` — отклонённый ввод откатывается синхронно до paint,
  принятый не трогается, отформатированный применяется сразу с кареткой, composition
  не прерывается; `order="manual"` — сохранённые не двигаются, двигаются при смене
  `orderKey`, prepend/append пачкой, наружу DOM-порядок; `render` в attached-контейнер
  не даёт ошибки stricterdom.
- stricterdom: чтение layout в mutate / запись в measure → ошибка с путём
  `Component > binding [phase]`; detached игнорируется; `selectionStart` в mutate
  → ошибка.

**Acceptance-тест рантайма.** Все `__dom_fixtures__` из `@solidjs/babel-plugin`
компилируются с нашей конфигурацией; каждый импортируемый символ экспортирован из
`frameact/dom`, фикстуры рендерятся без исключений.

**Бенч (Playwright: Chromium + WebKit, CPU throttling ×4, трейс).** Одно
приложение в трёх реализациях (teact, Solid 2.0, frameact; у frameact — варианты
A и B из §3.5 для списков):

| Сценарий | Метрика |
|---|---|
| Cold start: размер бандла, TTI на 1000 сообщений | кб, мс |
| Первичный рендер 1000 сообщений | время до первого кадра |
| Prepend/append по 50 сообщений | long tasks, forced layouts |
| Одна реакция изменилась в списке 1000 (A и B) | JS time, число compute/apply |
| Стриминг: текст одной строки каждый кадр 5 с | dropped frames, задержка данные→кадр (должна быть 0 кадров) |
| ChatList 100 чатов, случайный наверх каждые 100 мс, CSS-переезд | dropped frames, DOM moves (= 0 в manual) |
| Скролл с измерением sticky-заголовков и подгрузкой картинок | forced synchronous layouts |
| Blocking-анимация 300 мс + 20 обновлений стора | dropped frames **во время**, longest task **после релиза**, time-to-updated-frame |
| Композер: ввод 60 wpm с фильтром | input latency keypress→paint p95; откат до paint |
| 200 переключений чатов | heap после, рост `once`/контекстов |

Критерии v1:
- `enableStrict()` — 0 ошибок stricterdom на всех сценариях;
- из трейса: число `Layout` с ненулевым dirty внутри скрипта за кадр ≤ числа
  `requestForcedReflow`-задач этого кадра;
- после релиза гейта: longest task не хуже teact'овского pass'а на том же объёме;
- стриминг и реакции: обновление в том же кадре, что и запись (нет однокадрового
  отставания);
- паттерн B быстрее teact на «одна реакция в 1000» минимум в 3 раза; паттерн A — не
  медленнее teact;
- WebKit: те же инварианты фаз (порядок микротасков/MutationObserver, фолбэк `fastRaf`).

Если frameact не выигрывает у teact по этим пунктам — архитектура не оправдалась,
и это выясняется до написания клиента.

## 6. Вне скоупа v1

- Роутер, SSR, hydration, `Loading`/`Errored`-границы, async-мемо, optimistic,
  транзакции.
- Селекторы стора по путям (fine-grained подписки на части global).

## 7. Риски

- **Компилятор 2.0 — RC.** Выход эмиттера может измениться (включая форму
  `_$effect` и прямые присваивания). Защита: пин версии + acceptance-тест.
- **Дрен, читающий собственные добавления.** Делает возможным бесконечный цикл
  (эффекты дёргают друг друга). Guard считает **запуски одного эффекта** за дрен,
  а не число записей: эффект, запущенный 100 раз в одном дрене, считается циклом —
  `console.error` с его именем, его дальнейшие запуски переносятся на следующий кадр
  (dev и prod). Общего лимита записей нет: 10 000 независимых эффектов от одной записи
  применяются в одном кадре.
  Для `tickEnd` то же правило: счётчик запусков эффекта ведётся **за один дрен
  `flushTickEnd`** (эпоха дрена), а не за макрозадачу. Цикл — это самоподдерживающийся
  каскад без внешнего ввода; каждый `flushSync()` и каждый шаг `await` — новый дрен со
  свежим счётчиком, поэтому 5000 обновлений из сокета в `for await` или тысячи
  `flushSync()` подряд циклом не считаются. На 101-м запуске в дрене — `console.error`
  (один раз на эффект за дрен), запуск переносится на `setTimeout`: бесконечный цикл
  уступает event loop каждые 100 запусков. Общий self-dirty guard остаётся только для
  кастомных планировщиков; эффекты на `tickEnd` и кадровых очередях (и их
  `gateOnHeavyAnimation`-обёртках) он не считает повторно.
- **Правило «предок не CLEAN → выход».** Если предок по какой-то причине не будет
  перепланирован (ошибка в его compute), потомки застынут до следующего изменения
  предка. Ошибка в compute оставляет узел CLEAN (§3.2 п. 5) — потомки получат свой
  `run` при следующем загрязнении; тест на это обязателен.
- **Per-key memo в контейнерах** — память на 1000 строк × 40 ключей при паттерне A.
  Ленивое создание и бенч «200 переключений чатов» это контролируют; паттерн B
  рекомендован.
- **Семантика записи «сразу»** отличается от teact: код, рассчитывающий на
  `nextValue`-поведение, переносить буквально нельзя. Осознанно.

Два независимых ревьюера (оптика «мейнтейнер реактивного ядра» и «перф-инженер
telegram-tt») сошлись на трёх критических дефектах ревизии 1; всё ниже внесено.

## 10. Ревизия 3: стор — модель B

Решение ревизии 2 про стор (строка M1 в §9: контейнер = memo по пропсам + bridge-сигнал на scope,
`forceOnHeavyAnimation`/`forceSyncOnIOs` на bridge, то есть порт TeactN) заменено **моделью B** —
деревом сигналов с парковкой по причине (`F_STORE`): листья вместо контейнеров и `mapStateToProps`,
запись по пути на месте вместо иммутабельного `global`, гейт на уровне эффекта по причине грязности
вместо bridge-сигнала на scope. Актуальное описание — §3.5; обоснование и замеры — §3.5 (блок «Стоимость»). §9 оставлен как журнал ревизии 2.

## 11. Ревизия 4: кит готовности клиента (план 6)
