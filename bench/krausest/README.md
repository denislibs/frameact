# Бенчмарк krausest/js-framework-benchmark

frameact (keyed) в [js-framework-benchmark](https://github.com/krausest/js-framework-benchmark)
(коммит `bf894b681fb56433ccb6efb4a3c93e35eda2b20d`, master на 2026-10-04) рядом с Solid, Svelte, Vue, Preact
(signals и hooks) и vanillajs. Без форка: апстрим клонируется локально, наша реализация копируется в
`frameworks/keyed/frameact/`, ставятся и собираются только перечисленные семь реализаций, а не все 180+.

> Реализация frameact не в апстриме: **публичный PR невозможен, пока frameact не опубликован в npm**
> (апстрим требует зависимости из npm с фиксированными версиями и `package-lock.json` с адресами реестра).

## Что измеряется

Родные измерения апстрима (`webdriver-ts`, puppeteer-раннер, Chrome из `/Applications/Google Chrome.app`, видимое окно,
дефолты апстрима: 15 прогонов CPU-бенчмарков, троттлинг CPU ×4 для partial update / select / swap / clear и ×2 для remove):

- **CPU** (9): create 1k, replace 1k, partial update (каждая 10-я из 1k), select row, swap rows, remove row, create 10k,
  append 1k к 10k, clear. Длительность — по трейсу Chrome, от клика до конца отрисовки (`total` = script + paint).
- **Память** (3): после загрузки, после создания 1k строк, после 5 циклов create/clear 1k (по одному замеру).
- **Размер** (3): несжатый и brotli-размер файлов реализации, first paint.

Стартовые метрики lighthouse (`30_startup`) апстрим из набора по умолчанию убрал — здесь их нет.

**Не измеряется:** реальное приложение, фазы кадра (measure → mutate, heavy-animation gating, stricterdom), стор
(`frameact/store`), SSR, динамические списки `ManualFor` (ручной порядок). Бенчмарк — одна таблица из 1–10 тысяч однотипных строк;
итог не равен скорости мессенджера, ради которого frameact сделан.

## Запуск

```sh
pnpm bench:krausest                                    # всё: ~40 мин, откроет окна Chrome
node bench/krausest/run.mjs --check                    # установка + сборка + проверки корректности frameact, без замеров
node bench/krausest/run.mjs --check-all                # проверки для всех семи реализаций (в полный прогон входят)
node bench/krausest/run.mjs --count 3                  # дымовой прогон: 3 итерации вместо 15
node bench/krausest/run.mjs --frameworks frameact,solid
node bench/krausest/run.mjs --frameworks frameact --benchmark 01_ --keep   # перезапуск одного бенчмарка с досыпкой в results/
node bench/krausest/run.mjs --report                   # только пересобрать results/latest.md из results/raw/
```

Диагностика памяти и first paint тем же способом, что у апстрима, но с несколькими замерами, таймингами ресурса и снимками кучи по конструкторам: `node bench/krausest/heap.mjs --fw frameact,solid --fp 7 --trace | --mem 3 | --snap <dir>` (нужен поднятый сервер апстрима: `(cd bench/krausest/.upstream/server && PORT=8080 node_modules/.bin/tsx index.ts &)`; описание флагов — в шапке скрипта).

Нужны git, pnpm, npm, Node ≥ 22.12, сеть (клон и npm) и Google Chrome. Во время замеров держите окно Chrome на виду и
не трогайте мышь/клавиатуру (требование апстрима: иначе пропускаются paint-события), закройте тяжёлые программы.

`run.mjs`: клонирует апстрим в `.upstream/` (в .gitignore) на закреплённый коммит → делает `pnpm pack` от `src/` +
`package.json` frameact (корень репозитория тянул бы docs/тесты, ~80 МБ) и кладёт `vendor/frameact.tgz` в копию
`frameworks/keyed/frameact/` → `npm ci --ignore-scripts` по lock-файлам апстрима для остальных (для frameact —
`npm install`, lock генерируется: в нём хеш tarball'а, который меняется при каждой упаковке) → `build-prod` → поднимает
сервер апстрима → проверки апстрима для frameact (smoketest всех бенчмарков, `isKeyed`, CSP) → три прохода
`benchmarkRunner` (CPU, память, размер; ошибка в одном не теряет остальные) → `results/raw/*.json` +
`machine.json` + `latest.md` (`report.mjs`). Если 1-минутный load average > 8, ждёт до 5 минут, потом всё равно
запускается и записывает нагрузку. Результаты на нерабочей (корректность не прошла) реализации не считаются.

## Реализация (`frameworks/keyed/frameact/`)

Идиоматичный Solid-стиль, за образец — `frameworks/keyed/solid` апстрима: та же разметка, id и классы (включая
`aria-hidden` и `preloadicon`), `package.json` с `js-framework-benchmark` (`frameworkVersionFromPackage: "frameact"`),
сборка Vite + `frameact/vite` в `dist/main.js` (IIFE).

- `<For each={data()}>` (keyed по ссылке), одна `createSignal` на label строки, `createSelector` для выделенной строки
  (одно значение `selected` в состоянии, не флаг на строке — заметка #800 не применима), делегируемые события
  (`onClick` компилируется в делегирование; своего делегирования нет), никакого ручного DOM и своего `requestAnimationFrame`.
- Отличия от Solid-реализации: у frameact `createSelector(source)(key)` возвращает **accessor**, а не boolean
  (`const selected = isSelected(rowId); class={selected() ? "danger" : ""}`); нет `batch` — запись в сигнал никогда не
  запускает эффекты синхронно, всё сливается в одну mutate-фазу кадра. Кнопки — обычный компонент `Button`, без
  Solid-трюка со спредом массива и `prop:id`.
- `vite build --configLoader runner`: в tarball лежат исходники `src/*.ts` (пакет не собран), а Node не снимает типы
  у файлов из `node_modules`, поэтому нативный загрузчик конфига не может импортировать `frameact/vite`. После
  публикации (скомпилированный JS) флаг не нужен.
- Размер бандла: 37.6 КБ несжатый / 12.2 КБ brotli (Solid: 11.5 / 4.5 КБ); до прохода по памяти и бандлу было 45 / 14.6.

## Ограничения

- Локальный прогон на ноутбуке, за которым работал человек: **это не официальная таблица**, сравнивать с
  krausest.github.io нельзя, только строки внутри одной таблицы. Сравнение с реестром апстрима невозможно ещё и
  потому, что frameact — не npm-пакет.
- Окно Chrome, фоновая нагрузка (см. load average ниже), один замер для памяти — шумят. Доверительные интервалы
  CPU-ячеек узкие, но между прогонами медианы плавают на ±3–5 %: разницу в пределах этого не читать.
- Номера версий реализаций — те, что залочены у апстрима (Solid 1.9.3, Svelte 5.42.1, Vue 3.5.39, Preact 11.0.0 + signals 2.3.1);
  frameact — `0.0.0` из рабочего дерева (ветка `bench/krausest`, поверх core-perf).
- Метрика — `total` (script + paint), медиана, как по умолчанию на странице результатов апстрима. Основная часть `total` —
  нативные layout/paint (75–90 % для create/replace/swap/update), поэтому различия между фреймворками сжаты.

## Наблюдения

- **CPU — на уровне Solid.** Взвешенное геосреднее 1.13 против 1.12 (прошлый снимок 1.11 / 1.13; разница в шуме при нагрузке 5–15):
  frameact быстрее на clear/remove, медленнее на create/append/swap/select в пределах нескольких процентов `total`. Svelte на том же уровне (1.15), Vue
  (1.26) и обе preact (1.42 / 1.52) позади. Разброс между реализациями узкий (почти всё в 1.0–1.4 от vanilla), потому что
  75–90 % `total` в create/replace/swap/update — нативные layout/paint, одинаковые у всех.
- **Разница в основном в script-части трейса** (`results/raw/*.json`, поле `script`; paint-часть различается слабее и в обе стороны):
  create 1k 4.7 против 3.8 мс (было 5.2 против 4.0), create 10k 39.2 против 35.2 (45.5 против 36.8), replace 7.7 против 7.5 (9.2 против 8.0),
  swap 4.1 против 2.3 (при ×4 троттлинге), зато clear 13.8 против 16.7 и select 1.3 против 1.5 (remove: 1.1 против 0.8 — выигрыш по `total` — в paint).
  Проход по памяти убрал по аллокациям на строку (`Set`, `PropertyArray`, замыкание `run`): script на create/replace −10…−15 %.
- **Профиль (CPU-профайлер Chrome, без троттлинга, несжатая сборка; снят до прохода по памяти, скрипт разовый, в репозиторий не входит):** на create/replace
  JS-самовремя фреймворка — доли мс на 1k строк, в верхушке frameact: `applyTokens` (диффинг токенов `class` вместо
  присвоения `className` — цена правила «imperative `addExtraClass` переживает обновление»), создание узлов реактивного
  графа на строку (`createMutationEffect` / `Effect` / `initComputationNode`: как минимум эффекты `class` и label, оба
  в mutate-очереди кадра), узел селектора на строку (`observeSelector`, `SelectorProto.call` при удалении), `reconcileArrays`
  и `insertExpression`. Это и есть вероятная причина +4…6 % на create/replace/append: у Solid на строку те же два
  биндинга, но без регистрации в очереди фазы и без токенного диффа. На swap JS-самовремя у обоих ≈ 0.1–0.2 мс на операцию:
  разница 4.7 против 2.7 в трейсе — на пределе точности, объяснять её по одному профилю нельзя.
- **Память (разобрано в проходе по памяти и бандлу).** Куча на строку: у frameact было +216 Б против Solid. Причины и что сделано: узел
  эффекта/индекса/селектора не помещался во in-object-область V8 (размер выводится из синтаксических `this.x =` конструктора, поля из
  helper'а не считаются) — по `PropertyArray` на узел; теперь конструкторы присваивают поля явно и цепляются к конструктору
  Computation (−70 кБ на 1k строк). Канал `class` хранил на строку `Set` токенов + запись в `WeakMap` и дёргал `classList`
  (Blink выделял `DOMTokenList` + rare data на каждый `<tr>`): теперь состояние — символьные свойства на элементе, строка для
  0/1 токена, `classList` читается только при изменении (−107 Б/строку JS и −92 Б нативных). Встроенные планировщики кладут в очередь сам
  узел вместо замыкания `run` на эффект (−42 кБ на 1k строк). После очистки оставалась 64-кБ таблица `WeakMap`
  (`EphemeronHashTable` не сжимается): убрана вместе с `WeakMap`. ready +0.2 МБ — это код (источник скрипта, байткод): растёт с бандлом.
  Остаток разницы с Solid в run memory — нативная память Blink для того же DOM (≈ 10.3 кБ на строку), не JS.
- **Размер:** brotli 12.2 КБ (было 14.6; Solid 4.5, из семи реализаций больше только Vue 23.3). Что стало ленивым: контролируемые
  инпуты (`use:value`/`use:checked`) регистрирует Vite-плагин в модулях, где они есть (−1.5 КБ brotli); heavy-animation scope'ы и gate
  подключаются первым `begin()` (−0.8 КБ); списки с ручным порядком вынесены в `<ManualFor>` (−0.5 КБ). Что осталось: `mapArray` с тремя
  вариантами (≈ 3 КБ), ядро (≈ 30 КБ несжатых), нетронутые строки ошибок прода (≈ 250 Б).
- **First paint ≈ загрузка бандла, а не монтирование.** Сервер апстрима сжимает каждый ответ brotli (quality 11) на лету, ≈ 1 мс на
  несжатый кБ; от `responseEnd` скрипта до first paint у frameact те же ≈ 32 мс, что у Solid и vanillajs — монтирование синхронное
  (`render` применяет mutate-эффекты сразу). Каждый кБ бандла — это миллисекунда first paint в этом харнессе.
- **API-нюанс при портировании:** `createSelector(key)` возвращает accessor, а не boolean, как в Solid. Забыть вызов `()`
  — молча выделить все строки; именно это поймал `04_select1k` на первом прогоне.
- Корректность/идиоматичность: никаких заметок апстрима (#772, #796, #800, #801) к реализации не применимо — rAF и
  делегирование внутри фреймворка, выделение хранится одним сигналом, DOM руками не трогается.
